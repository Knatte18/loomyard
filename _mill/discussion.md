## Problem

Slice 3 of the `fabric-unified-view` campaign (see `manifest/designs/fabric-unified-view.md`, "Build order", slice 3). Landing slice 2 (`Fabric.Commit` classify-and-dispatch, now in `internal/fabricengine/commit.go`) surfaced an asymmetry: `Fabric.Commit` acquires the fabric write lock (`.weft/weft.write.lock`) **only when the commit has weft-side files**. A warp-only `Fabric.Commit` — no weft-side paths, or `opts.SkipGit` set — runs unlocked `git add`/`git commit` on the warp (host) repo. So two concurrent warp-only `Fabric.Commit` calls race directly, with no mediation.

Separately, every landed `Fabric.Commit` spawns its own independent detached push child (`SpawnDetachedPush` in `spawn.go`). The only dedup today is `gitrepo.PushCoalesced`'s per-repo lock, which lets a late arrival no-op fast once it acquires the lock — but each call still pays the full fork + CLI-reentry + lock-acquire cost, and each does a single guarded push rather than looping to absorb commits that land during the push window. `internal/boardengine`'s `Sync` already solves the coalescing shape better: it loops commit-then-push under one absorbing push lock until nothing is dirty, collapsing a burst of writers into as few real push operations as possible. Fabric should own that generalized coalescing; `boardengine.Sync` should then delegate to it rather than keep a parallel implementation (board's storage lives in `weft:main` and fabric is the git module now — board reimplementing git-level concurrency serialization is a layering inversion).

**Why now:** slice 3 is sequenced immediately after slice 2 and before slice 4 (snapshot-as-trailer) because both touch the same `commit.go`/`weftgit.go` surface — landing this first avoids reworking it twice.

## Scope

**In:**

- A **combined fabric write lock** taken by *every* `Fabric.Commit` call regardless of side (warp-only, weft-only, both), closing the warp-only unlocked race. Reuses the existing `.weft/weft.write.lock` that `CommitWeft` already acquires.
- A **loop-until-clean push/commit coalescing** primitive in `internal/fabricengine`, holding one absorbing push lock across the loop, generalized from `boardengine.Sync`. Parameterized by caller-supplied commit-step and push-step closures.
- `Fabric.Commit`'s async push rewired so its detached child runs the coalescing loop (push-only) instead of a single `SpawnDetachedPush` → per-side `PushCoalesced`.
- `boardengine.Sync` **delegates** to the new fabricengine coalescing primitive, passing its own `board.lock`-guarded commit closure and rebase-retry push closure; board keeps `board.lock`, `board.push.lock`, and `ensureLockfilesIgnored` behavior unchanged.
- A **rebase-free push primitive** for the fabric async path (`gitrepo` today exposes only rebase-retry push variants). The fabric loop's warp/weft push uses it; the board loop's push uses the existing rebase-retry variant.
- Elimination of the host-root `.gitrepo-push.lock` artifact on the warp-via-fabric path (see Decisions).

**Out:**

- **Warp-rebase / remote-reconcile** (pull, rebase, conflict resolution). This is slice 6, deliberately. Slice 3's async push is rebase-free and leaves a diverged remote's commits unpushed; it never mutates the working tree.
- **LLM-driven conflict resolution and any agent spawn.** The spawn lives *above* fabric, in orchestration (`finalize`/`loom`), never in fabricengine (see the "Conflict-resolution spawning stays above fabric" decision). Nothing in this slice reaches for it.
- **Snapshot-as-trailer** (slice 4), clone/init changes (slice 5), and any change to `hubgeometry`'s geometry ownership beyond a new base-taking accessor if one is needed.
- **`internal/perchcli`'s still-unanchored block-exit commit** and other pre-existing Weft-Git-Invariant cleanups — not this slice's concern.
- Any change to how humans use raw git in the warp worktree. Warp stays ordinary git; fabric locks only mediate fabric-driven writes.

## Decisions

### combined-commit-lock

- **Decision:** `Fabric.Commit` acquires one lock for every call, regardless of which side(s) the files land on, by reusing the existing `.weft/weft.write.lock`. `CommitWeft` already acquires the same lock, so the two serialize against each other on the weft side as before, and warp-only `Fabric.Commit` calls now serialize too.
- **Rationale:** Slice 2 already holds the weft lock across *both* commits of a two-sided `Fabric.Commit` (acquired at `commit.go:108-118`, before the warp commit at line 122 and the weft commit at line 132). The only gap is the warp-only path, which takes no lock at all. Making that path acquire the same lock is the minimal, consistent fix. `Fabric.Commit` is the sole warp-side writer via fabric (humans use raw git independently and cannot be locked regardless), so the only warp race is two concurrent `Fabric.Commit` calls — which one shared lock fixes. The over-serialization (a warp-only commit blocking an unrelated weft-only commit) is negligible: both are fast local commits touching different repos, and the events rarely coincide.
- **Rejected:** *Two locks (warp + weft) taken in a fixed order* — reintroduces lock-ordering as a live invariant and requires ripping up slice 2's existing "one lock across both commits" structure, for marginal concurrency between events that almost never coincide. *A warp-only lock taken only when warp files are present* — same restructuring cost, and it leaves warp-only and weft-only calls never serializing against each other, which is exactly the "regardless of which side it touches" property the brief asks for.

### commit-lock-scoped-to-commit-only

- **Decision:** The combined write lock is held **only around the commit(s)** — acquire, warp commit, weft commit, release — and is released **before** the async push is spawned. The time-consuming network push runs afterward, in the detached child, under a **separate** absorbing push lock.
- **Rationale:** The commit lock protects a fast, local critical section (git index + commit). Holding it across the slow, network-bound push would serialize commits behind pushes for no reason and could stall the calling thread's next commit. The two concerns — commit serialization and push coalescing — are independent and get independent locks.
- **Rejected:** A single lock covering commit *and* push — couples a fast local operation to a slow network one and defeats the whole point of an async, non-blocking push.

### coalescing-loop-in-fabricengine-via-closures

- **Decision:** `internal/fabricengine` owns a coalescing primitive. Its contract, made precise here (resolving round-1 review gaps on lock ownership and the exit condition):
  - **Absorbing-lock ownership — the primitive acquires and holds it, at a caller-supplied lock *path*.** The primitive takes an absorbing-push-lock path argument, `AcquireWriteLock`s it once, and holds it across the whole loop, releasing on return. `boardengine.Sync` passes its existing `board.push.lock` path (so board's lock file is unchanged in name and location — only the *acquire site* moves into the primitive); `Fabric.Commit`'s detached child passes a new `.weft/`-based fabric push lock (see lock-artifacts-never-at-worktree-root for the constant). There is exactly **one** absorbing lock per caller, owned by the primitive — never a second, redundant lock and never a double-acquire. Passing a single lock-*path* argument is deliberately narrower than the rejected full data bundle (lock paths + stageAll flag + message): the commit/stage/message policy stays entirely in the closures; only the lock path crosses the boundary.
  - **One exit contract — the step closure returns `(progressed bool, err error)`; the loop repeats while `progressed`, exits on the first no-progress iteration.** This is the single terminator for both callers; the exit condition is the step's return value, not a separate closure.
  - **The step closures.** `boardengine.Sync` passes a step that commits-dirty (under `board.lock`) then rebase-retry-pushes, returning `progressed = committed` (matches today's `!committed` exit at `sync.go:78`). `Fabric.Commit`'s detached child passes a step that does no commit (commits already landed synchronously in `Fabric.Commit`) and a **rebase-free** two-sided push, returning `progressed = (warp HEAD advanced) OR (weft HEAD advanced)` since that iteration's pre-push snapshot — so the loop absorbs new commits on **either** side and exits only when neither HEAD moved during the push window.
- **Rationale:** The absorbing-lock + loop-until-clean *is* the git-level concurrency-serialization logic; moving it into fabricengine is exactly what removes board's layering inversion, satisfying the brief's "board delegates" requirement. Closures keep the repo-specific policy — board's `StageAllAndCommit` + `board.lock` + rebase-retry push, versus fabric's two-sided rebase-free push — out of the shared loop, so the loop stays a pure coordination skeleton. Crucially, the **rebase policy lives in each caller's push closure**, not in the loop: board (safe, dedicated storage tree) keeps rebase-retry; fabric (live agent worktree) uses rebase-free. See rebase-free-async-push. The `progressed`-bool exit unifies board's commit-driven terminator and fabric's HEAD-stability terminator into one contract without the loop needing to know which policy produced the bool.
- **Rejected:** *A fully-parameterized data function* (lock paths + stageAll flag + message) — less flexible for fabric's two-sided push and would force board's stage-all semantics and commit message into the shared function's signature; note the single absorbing-lock-*path* argument the accepted design does pass is not this bundle — it carries no stage/message policy. *A separate caller-supplied terminator closure* distinct from the step — more moving parts than the `progressed` bool the step already computes for free. *Generalizing `gitrepo.PushCoalesced` into a loop at the gitrepo layer* — board's coalescing includes the *commit* step, which is above gitrepo's scope; and gitrepo is geometry-blind, so it cannot own the loop's lock placement policy.

### always-spawn-detached-child

- **Decision:** Every landed `Fabric.Commit` spawns a detached child that runs the coalescing loop; the child is never `Wait()`ed. Mirror `boardengine`'s always-spawn model exactly.
- **Rationale:** The loop's win is fewer *real* pushes plus one process absorbing commits that land during its push window; the first child to acquire the absorbing lock loops until stable, and later children block, then find nothing and exit fast — board's proven, race-free pattern. The per-call fork remains, which is acceptable: board forks per write too, and the brief holds board up as the good model.
- **Rejected:** *Skip-spawn-if-a-pusher-is-active (TryLock)* — fewer forks, but introduces a lost-wakeup risk: a commit landing exactly as the active pusher finishes its final `hasUnpushed` check and releases could be missed. Board avoids this precisely by always spawning.

### push-only-loop-exit-on-head-stability

- **Decision:** The fabric async push child's loop is **push-only** (no commit step). Its exit condition is **HEAD-SHA stability**, expressed through the unified `progressed`-bool step contract (see coalescing-loop-in-fabricengine-via-closures): the push step returns `progressed = (warp HEAD advanced) OR (weft HEAD advanced)` since its pre-push snapshot; the loop repeats while `progressed` and exits on the first iteration where neither HEAD moved during the push window. It does **not** loop on raw `hasUnpushed`.
- **Rationale:** `boardengine.Sync` exits on `!committed` because its loop *commits* (a clean tree is the natural terminator). A push-only loop has no commit step, so it needs a different terminator. Looping on `hasUnpushed` risks the exact infinite spin `gitrepo.PushCoalesced`'s doc warns about: with no upstream configured, `hasUnpushed` stays permanently true. Keying the exit on "did new local commits appear during the last push" both absorbs genuinely-new work and terminates deterministically. A push that is *rejected* (diverged remote, rebase-free — see below) also terminates the loop rather than retrying the same rejected push.
- **Rejected:** Loop on `hasUnpushed` — the documented spin hazard. Cap iterations by count only — works but is a blunter instrument than HEAD-SHA stability, which exits exactly when there is no new work.

### rebase-free-async-push

- **Decision:** The fabric async coalescing push is **rebase-free**: a plain `git push`, never `git pull --rebase`. When git rejects the push because the remote has diverged, the child logs the unpushed state and exits. Remote reconciliation (pull + rebase + conflict resolution) is **not** the async push's job — it is deferred to slice 6, driven by an orchestrator at a controlled boundary. `boardengine`'s push closure keeps rebase-retry (its `weft:main` storage checkout is machine-owned and hand-edited by no one, so rebasing it is both safe and necessary for multi-machine convergence).
- **Rationale:** A plain `git push` never touches the working tree — it reads refs and sends objects — so it is safe to run async while the calling thread continues editing. `git pull --rebase` is the *only* operation in the current push chain that mutates the working tree. On warp — the agent's *live* worktree — that is unsafe: the tree is almost always dirty (mid-edit), so `pull --rebase` aborts and the push fails silently; and were the tree clean, a rebase could raise conflicts needing an LLM *after control has already returned to the calling thread*. Making the async push rebase-free is precisely what makes returning control to the thread safe: the only thing the background child does is a network push that either succeeds or leaves commits local. This matches `manifest/designs/fabric-unified-view.md`'s "Warp-rebase and remote-reconcile" layering — "fabric core detects and precomputes the diff; an orchestrator above it spawns the LLM ... never an LLM deciding weft-commit timing." The user confirmed push need not always succeed ("I notice fast if the net drops; no long-lived daemon standing and waiting").
- **Rejected:** *Slice 3 handles reconcile now* — pulls slice-6 scope (pull + rebase + LLM conflict resolution at a controlled boundary) into this task; far larger, and out of sequence. *Async push from a dedicated shadow checkout* so a rebase never touches the agent's tree — extra per-repo worktree infrastructure, heavier, slice-5/6 territory.

### conflict-resolution-spawning-stays-above-fabric

- **Decision:** Fabric does **not** own LLM-driven conflict resolution or any agent spawn. Fabric owns the deterministic *mechanism* of reconcile (divergence detection via `SHAExists`, correspondence re-anchor via `RevertWithWeft` nearest-older, and precomputing a conflict as a plain document per finalize.md's document-driven pattern). The *spawn* — deciding which agent/model, when, and handing it the document — lives in the orchestration layer (`finalize`/`loom`), which is Go and already imports fabricengine. This decision is recorded now as a scope boundary even though its consumer is slice 6, so slice 3's rebase-free async push has a documented rationale for leaving divergence alone rather than reaching for reconcile.
- **Rationale:** Two reasons, one decisive. (1) **Import cycle — not negotiable:** `loomengine`, `websterengine`, and `perchengine` all import `fabricengine`. For fabric to spawn an LLM it would import the agent-exec stack (shuttle/reed/loom/webster), closing a cycle `fabricengine → loomengine → fabricengine` that Go will not compile. Fabric's current production imports are all low-level (`gitexec`, `gitrepo`, `hubgeometry`, `lock`, `proc`, `state`, `fslink`, config/yaml) — no agent stack. (2) **Scope + testability:** the design doc scopes fabric as "the one-repo illusion portal, nothing more"; conflict-resolution policy is orchestration, not git mechanics. Keeping the spawn above fabric keeps fabric deterministic and unit-testable, which is the whole lyx thesis ("the deterministic Go responsibility ... an agent-run weft commit reintroduces the non-deterministic, untestable orchestration lyx exists to remove"). The user's own observation — "Go must spawn the LLM anyway" — is the answer, not a counter: the LLM *is* spawned by Go, by `finalize`, a Go layer that sits above fabric, not by fabric.
- **Rejected:** *Build LLM conflict-resolution into fabricengine* — blocked outright by the import cycle, and it would collapse fabric's scope boundary and its deterministic-testability property.

### lock-artifacts-never-at-worktree-root

- **Decision:** No fabric lock file sits at a worktree root. The combined commit lock stays at `.weft/weft.write.lock` (weft-side, already git-excluded via `seedWeftArtifactExcludes`). The new absorbing push lock lives alongside it under `.weft/`, **named by a pinned constant** in the same style as `weftWriteLockFile = "weft.write.lock"` (`weftgit.go:28`): add `weftPushLockFile = "fabric.push.lock"` (final spelling is mill-plan's to pin, but it must be a named constant, not an inline literal, and `seedWeftArtifactExcludes` must git-exclude it alongside the existing `.weft/` and push-lock entries). The host-root `.gitrepo-push.lock` artifact (created today when fabric pushes warp via `PushCoalesced`) is **eliminated** on the warp-via-fabric path, not relocated.
- **Rationale:** The host (warp) repo is the pristine, human-facing project repo; a `.gitrepo-push.lock` appearing untracked at its root is dirt (the weft side git-excludes it, the host side does not). Because the fabric async push is now rebase-free *and* fabric's absorbing push lock already serializes the loop *and* fabric is warp's only pusher, the warp push inside the loop can be a lock-free rebase-free `git push` — so `gitrepo.PushCoalesced`'s per-repo lock file is never created at the host root at all. This is strictly cleaner than relocating it and avoids forcing a `.lyx`/geometry concern onto geometry-blind `gitrepo` (which does not import `hubgeometry` and must not). `gitrepo.PushCoalesced` stays in use for board (its lock lives in the board dir) and for weft-side `PushWeft` (weft-side, git-excluded) — neither is in the pristine host, so neither is dirt.
- **Rejected:** *Relocate `gitrepo`'s `.gitrepo-push.lock` under `.lyx/`* — would require `gitrepo` to know `.lyx` geometry (breaking its geometry-blindness and the gitrepo Client Boundary Invariant) or take a lock-dir parameter; eliminating the artifact on the fabric path is simpler and touches no gitrepo boundary. *Seed a host-side git-exclude for it* — hides the artifact but still creates it and adds host-repo exclude-seeding fabric otherwise avoids.

Concurrency-in-process note for tests: `gofrs/flock` uses OS file locks; two separate `flock.New` handles (each `AcquireWriteLock` creates one) contend even within a single process, so concurrent goroutines each calling `Fabric.Commit`/the loop exercise the real lock — process-spawning is not required to test serialization.

## Constraints

From `CONSTRAINTS.md` (read this session):

- **Weft Git Invariant** — all weft git goes through `internal/fabricengine`, driven by Go orchestration in-process, never an LLM agent. This slice's weft push/commit stays inside fabricengine. The "Orchestration, not agent" clause is exactly what the conflict-resolution-spawning-stays-above-fabric decision upholds: fabric provides the mechanism; the loop owner (loom/finalize) controls timing and any agent spawn. Board's carve-out (any LLM session may trigger a board write via `lyx board <verb>`) is unaffected — board's git still flows through `CommitWeftAt`/`PushWeftAt`.

Any `.lyx`-based lock path must come from a hubgeometry accessor, not a literal in fabricengine. The chosen design keeps locks under `.weft/` (`weftLockDirName`, already a fabricengine-local constant, not a hubgeometry token) — verify `.weft` is not a reserved geometry token (it is fabric's own lock-dir name, defined in `weftgit.go`, and predates this slice).
- **gitrepo Client Boundary Invariant** — `internal/gitrepo` splits go-git (local reads) from `gitexec` (remote/working-tree mutations); the CLI-bound method set is pinned in `cmd/lyx/gitrepoboundary_test.go` and enumerated in CONSTRAINTS.md. **Adding a rebase-free push method to `gitrepo` that shells out via `gitexec` requires updating both the pinned test set and the CONSTRAINTS.md gitrepo entry in the same commit** — a new `gitexec` call inside gitrepo without editing that list is itself a violation.
- **Test Tier Purity Invariant** — untagged test files perform no git spawns (no `gitexec.RunGit`, `exec.Command`, `lyxtest.Copy*`). Concurrency/real-git tests must be `//go:build integration` tagged.
- **Hermetic Git Test Environment Invariant** — every git-spawning test package needs a `TestMain` calling `lyxtest.HermeticGitEnv()`. `fabricengine` and `boardengine` already have `testmain_test.go`; new integration tests inherit it.
- **Documentation Lifecycle / task-completion docs** — `internal/fabricengine/doc.go`'s package comment must be updated in the same commit (the durable design folds there per the design doc); if the module table or execution stack changes, `docs/overview.md`; the slice-3 line in `manifest/designs/fabric-unified-view.md`'s Build order marks DONE, and its two slice-3 open questions ("Warp-side lock shape", "Where the coalescing loop lives") are resolved inline the way slices 1-2 recorded theirs. `manifest/roadmap.md` does not move (this is a planned slice completing, tracked in the design doc, not a roadmap-level item — confirm against the roadmap's own conventions).

## Testing

TDD candidates and required scenarios (real-git, `//go:build integration` unless noted):

- **Warp-only commit serialization** (fabricengine) — the headline fix. Two concurrent warp-only `Fabric.Commit` calls against a real warp+weft pair must serialize on the combined lock: assert both commits land, neither corrupts the other's index, and the resulting history is linear. This is the test that would fail against today's unlocked warp-only path.
- **Combined-lock coverage across sides** — a warp-only, a weft-only, and a two-sided `Fabric.Commit` all contend on the same `.weft/weft.write.lock`; assert mutual exclusion (e.g. via an observable ordering or a lock-held probe).
- **Commit lock released before push** — assert the write lock is not held during the async push (e.g. the push child can run while a subsequent commit proceeds). Guards commit-lock-scoped-to-commit-only.
- **Push coalescing loop-exit on HEAD stability** (unit-testable in isolation) — drive the loop with a scripted push-step and HEAD-SHA sequence: it loops while new commits appear during a push and exits once HEAD is stable. Explicitly test the no-upstream case does **not** spin (the `hasUnpushed`-always-true hazard).
- **Rebase-free async push leaves divergence** — with a diverged remote, the fabric async push is rejected, leaves commits unpushed, mutates **no** working-tree file, and never runs `pull --rebase`. Contrast: board's push closure *does* rebase-retry and converges. Two separate tests (fabric path, board path) sharing a diverged-remote fixture.
- **No host-root `.gitrepo-push.lock`** — after a warp-via-fabric push, assert `.gitrepo-push.lock` does **not** exist at the warp worktree root (eliminated), while board's and weft's own push locks are unaffected in their (git-excluded) homes.
- **board delegation parity** (boardengine) — `boardengine.Sync` after delegating to the fabricengine primitive still: coalesces a burst of writes into as few pushes as possible, keeps `board.lock`/`board.push.lock` semantics, and seeds `.gitignore` via `ensureLockfilesIgnored`. Re-run/extend the existing board sync tests to prove no behavioral regression.
- **Fabric.Commit push-on-partial-failure** — on a `PartialCommitError` (warp landed, weft failed), the async push still fires for the landed warp commit (keep current behavior). Assert the push is spawned when `WarpCommitted || WeftCommitted`.
- **`gitrepo` rebase-free push primitive** — a focused test that the new primitive pushes without ever invoking `pull --rebase`, and still establishes upstream on first push (`push.autoSetupRemote=true`), mirroring the existing push tests.

Do not over-specify assertion shapes — mill-plan owns that. The integration substrate (`lyxtest` paired warp+weft fixtures, `WEFT_SKIP_*` gating, the `spawnDetachedPushFn` seam) is already established by slice-2's `commit_integration_test.go` / `commit_partial_integration_test.go`; new tests build on it.

## Q&A log

- **Q:** Warp-side commit-lock shape — single combined lock, two locks in fixed order, or a warp-only lock taken only when warp files present? **A:** Single combined lock (reuse `.weft/weft.write.lock`), taken by every `Fabric.Commit` call. Simpler and consistent with slice 2's existing "one lock across both commits"; the sole warp-side writer is `Fabric.Commit`, so one shared lock closes the only warp race.
- **Q:** Where does the coalescing loop live and in what shape? **A:** In `fabricengine`, as an absorbing-lock loop-until-clean parameterized by commit/push closures; board delegates and keeps `board.lock`. Fewer real pushes is nice-to-have but never at the cost of blocking the main process — fire-and-forget detached child is mandatory.
- **Q:** `Fabric.Commit` push model — always spawn a detached loop child, or skip-spawn when a pusher is active? **A:** Always spawn (mirror board); the TryLock skip introduces a lost-wakeup risk board avoids by always spawning.
- **Q:** Test approach? **A:** Integration (real git, tagged) for concurrency + unit tests for the loop-exit; required anyway by the Test Tier Purity Invariant.
- **Q:** The host push-lock artifact `.gitrepo-push.lock` appears at the pristine host worktree root — in scope, and where should it go? **A:** In scope. Lock files must not sit at worktree root; they belong in git-ignored, hubgeometry-managed locations. Resolved by *eliminating* it on the warp-via-fabric path (rebase-free, lock-free warp push under fabric's absorbing lock) rather than relocating gitrepo's geometry-blind lock.
- **Q:** Is the combined lock taken during push too, or only commit? Push is the time-consuming part. **A:** Only around the commit; released before the async push. Push has its own separate absorbing push lock in the detached child.
- **Q:** Failure handling if the async push hits a diverged remote needing rebase — retry, or give up? No long-lived daemon wanted. **A:** Rebase-free push: on rejection, log and exit, leaving commits unpushed; the next `Fabric.Commit` retries. No backoff daemon. It's fine if push doesn't always succeed.
- **Q:** But if the async push runs `pull --rebase` while the calling thread keeps editing — concurrent tree mutation, and rebase conflicts an LLM must fix, after control already returned to the thread? **A:** Exactly why the async push is rebase-free. Only `pull --rebase` mutates the working tree; a plain `git push` does not, so returning control is safe. Rebase/remote-reconcile is slice 6, driven by an orchestrator at a controlled boundary — never inside the fire-and-forget push.
- **Q:** (review r1 gap) Who acquires the absorbing push lock — the primitive or the caller — and how does board keep `board.push.lock` unchanged without lock-path parameterization? **A:** The primitive acquires and holds it, at a caller-supplied lock *path*. board passes its existing `board.push.lock` path (name/location unchanged; only the acquire site moves into the primitive); fabric passes a new `.weft/` push lock. One absorbing lock per caller, no double-lock. A single lock-path argument is narrower than the rejected full data bundle — stage/message policy stays in the closures.
- **Q:** (review r1 gap) What is the single loop-exit contract for the shared primitive, given board exits on `!committed` and fabric on HEAD stability across two repos? **A:** The step closure returns `(progressed bool, err)`; the loop repeats while `progressed` and exits on the first no-progress iteration. board returns `progressed = committed`; fabric returns `progressed = warp-HEAD-advanced OR weft-HEAD-advanced`. Exit keys on **either** fabric repo's HEAD, not a separate terminator closure.
- **Q:** Since finalize (Go) must spawn the conflict-resolving LLM anyway, should fabric just own that built-in? **A:** No. `loomengine`/`websterengine`/`perchengine` import `fabricengine`, so fabric importing the agent-spawn stack closes a compile-breaking import cycle. Fabric owns the deterministic reconcile *mechanism* (detect, precompute conflict-as-document); the *spawn* lives above fabric in `finalize`/`loom`, which is Go and already imports fabric. Recorded as a scope boundary; slice 3 builds none of it.
