# Discussion: board: move storage to weft:main

```yaml
task: 'board: move storage to weft:main'
slug: board
status: discussing
parent: main
```

## Problem

`board` (lyx's task-tracker) currently stores its data (`tasks.json` + rendered `Home.md`/`_Sidebar.md`) in a separate git repo, cloned into `<hub>/_board` at hub-bootstrap time (`fabricengine.CloneHub`'s board-clone step, `internal/boardengine`'s own `gitrepo`-based commit/push). By default this separate repo is derived as the host repo's `.wiki.git` remote — reusing GitHub's free per-repo wiki git slot as convenient hosting, but never relying on GitHub's Wiki *rendering* feature (which would require the host repo to be public — a disqualifying problem for private consulting work).

This is extra repo-management overhead for something that doesn't need its own git identity, and (per `CONSTRAINTS.md`'s Weft Git Invariant) it is architecturally isolated from the rest of lyx's git-coordination story (`internal/fabricengine`), which every other durable, cross-machine lyx artifact goes through. The fix: board joins the same `weft` repo everything else lyx-related already lives in (raddle, `PATTERN.md`, per-task discussion/plan artifacts), on a reserved branch — `weft:main` — rather than a separate repo. `weft:main` is permanently unclaimable by any task's own weft branch (every task's weft branch is `<slug>-weft`, enforced uniformly, no exceptions), which is what makes reserving it for board safe.

This task is Planned #1 in `manifest/roadmap.md`, sequenced immediately before `fabric: unified-repo view` (Planned #2, not yet built) — that later item explicitly depends on this one shipping first ("inherits a 2-repo clone... introduces prime's second weft checkout... hardens `suffixWeftPrimaryBranch` for the `weft:main` case first"). This task is therefore the first to introduce prime's second weft worktree checkout, not just a data-format change.

## Decisions

### Weft git routing — new fabricengine primitives, board keeps its own architecture

- Decision: `internal/boardengine` keeps its existing detached-sync architecture exactly as it is today — a mutating CLI call takes the write lock, mutates the store, renders, saves to disk, and returns immediately after launching a detached `lyx board sync` child process (`spawn.go`, unchanged); *all* actual git operations (both commit and push — not just push) happen inside that detached child, never blocking the calling process. Only the git *backend* changes: today's `Sync()` constructs exactly **one** `gitrepo.New(boardPath)` handle and reuses it for both `commitDirty`'s `StageAllAndCommit` call and its own `PushCoalesced` call — swap those two method calls (not two separate `New` calls) for the package-level `CommitWeftAt`/`PushWeftAt` functions in `internal/fabricengine`.
- New fabricengine primitive: `CommitWeftAt(weftPath, message string, opts SyncOptions) (sha string, committed bool, err error)` in `weftgit.go`, next to the existing `PushWeftAt(weftPath, opts)`. Both are package-level functions taking only a weft path — no `Fabric`/warp pairing required. `CommitWeftAt` wraps `gitrepo.New(weftPath).StageAllAndCommit(message)` (wildcard-stage, no pathspec) — no `Warp-SHA` trailer, no correspondence recording.
- Rationale: the existing `Fabric.CommitWeft` method cannot be reused as-is — it unconditionally derives a `Warp-SHA` trailer from `f.Warp.CurrentSHA()` and calls `RecordCorrespondence`. `_board`'s `weft:main` checkout has no corresponding warp branch (per the design doc: "a separate, standalone concern, not routed through `fabric.SyncWeft`/`fabric.RevertWithWeft`"), so attaching a trailer would tag board commits with a meaningless pointer at whatever prime's host HEAD happens to be. `PushWeftAt` already has exactly the right shape (warp-untethered, package-level) — `CommitWeftAt` is its natural commit-side counterpart.
- The wildcard-stage (`StageAllAndCommit`) call is not a new liberty: `internal/gitrepo/doc.go` already documents this exact escape hatch as **"board's opt-in exception"** to the explicit-pathspec-only rule every other consumer (`fabric`, `raddle`, `codeintel`) follows — safe specifically because `_board` is a dedicated worktree nothing else ever writes into (unlike the shared `_lyx` tree `CommitWeft`'s pathspec-filtering exists to protect). Today `boardengine` calls it directly; after this task, `fabricengine.CommitWeftAt` calls it on board's behalf. Both `gitrepo/doc.go`'s and `fabricengine/doc.go`'s doc comments describing this need updating in the same commit (see Scope).
- `boardengine`'s own `BOARD_SKIP_GIT`/`BOARD_SKIP_PUSH` env-driven `Config.SkipGit`/`SkipPush` fields stay the sole source of truth for board's skip behavior — construct `fabricengine.SyncOptions{SkipGit, SkipPush}` explicitly from them. Do **not** call `fabricengine.EnvSyncOptions()` (which reads its own, different `WEFT_SKIP_GIT`/`WEFT_SKIP_PUSH` env vars) — that would introduce a second, competing skip-gate for the same behavior.
- Lock/manifest exclusion (`.gitignore`-based, today's `ensureLockfilesIgnored`: `*.lock`, `*.swaplock`, the `.board-rendered.json` render-manifest sidecar) stays entirely `boardengine`'s own responsibility, unchanged in ordering — still called inside `Sync()` before the commit step, exactly as today. `CommitWeftAt` itself is a bare, unopinionated wildcard-commit primitive with no exclude logic baked in, deliberately mirroring `PushWeftAt`'s equally bare shape: lock-file naming is board-specific, not a cross-module concern the way `_lyx`'s shared-tree exclusion (`seedWeftArtifactExcludes`) is, so it does not belong in `fabricengine`. On `_board`'s very first-ever write (a freshly orphan-created worktree, see the `_board` worktree decision below), `ensureLockfilesIgnored`'s `.gitignore` write happens before `StageAllAndCommit` is called — same ordering as today — so lock/manifest files are never staged even on that first commit.
- CONSTRAINTS.md consequence: the Weft Git Invariant's "Orchestration, not agent" framing (weft-commit timing controlled by a phase-boundary loop owner) does not literally hold for board — board's writes are agent-write-timed by design (any LLM session, any worktree, any time — that is the entire point of board's shared-visibility model). Record this explicitly as a narrow, deliberate carve-out in `CONSTRAINTS.md`'s Weft Git Invariant section, in the same commit: "Module ownership" (all weft git through `fabricengine`) still holds without exception; the timing-control bullet is scoped to `fabricengine`'s other callers (loom/perch/builder/webster round-loop commits), with board named as the one exception, its rationale, and a forward pointer to `fabric-unified-view.md`'s `Fabric.Commit` work (sequenced after this task) as where the general "who may time a weft commit" question gets a fuller answer.
- Rejected: routing `lyx board <verb>` synchronously through `fabricengine` with no detached process (reintroduces the multi-second push latency the current detached design exists to avoid — the user was explicit that push, and preferably any slow remote op, must never block Go); a separate periodic-flush daemon decoupling commit timing further (unrequested complexity beyond what the user asked for).

### `_board` becomes a second weft worktree, not a separate clone

- Decision: `<hub>/_board` keeps its existing name and `hubgeometry.BoardDir(hub)` accessor unchanged. It becomes `git worktree add <hub>/_board <hostBranch>` inside the weft repo whose root is `hubgeometry.WeftRepoRoot()` (the same repo prime's own `<name>-weft` checkout belongs to), instead of `cloneRepo(boardURL, ...)` of a separate `.wiki.git` remote.
- **Precise post-clone branch state (corrected in discussion review r5 — the original "adopt origin as a tracking local branch" framing doesn't match git's actual clone behavior):** `cloneRepo(weftURL, weftPath)` is a plain `git clone`, which — on any non-empty weft remote — already creates a **local** `<hostBranch>` ref tracking `origin/<hostBranch>` and checks it out. `suffixWeftPrimaryBranch`'s subsequent `checkout -b <hostBranch>-weft` moves HEAD away from it but does not delete or touch that local `<hostBranch>` ref. So by the time `_board`'s worktree-add runs, `<hostBranch>` already exists locally in the ordinary (first-ever setup) case **and** in a `--reset` re-clone of a hub with existing board history (both hit the identical code path — a fresh `git clone` each time) — no `-b`/`--track` "adopt" flag is needed or valid; a literal `-b <hostBranch> --track origin/<hostBranch>` form would fail outright with "branch already exists." The correct call is a **plain** `git worktree add <path> <hostBranch>` against that already-existing local branch. The only state that genuinely needs the separate **orphan**-creation path (see below) is a truly empty weft remote, where clone leaves no local `<hostBranch>` ref at all.
- **Not a hardcoded "main"**: everywhere in this document (including this task's own title/slug) "main" is used as the illustrative/common-case name, matching this actual hub's reality — but the branch name itself must be **derived dynamically**, never a hardcoded literal, exactly as `suffixWeftPrimaryBranch` already derives it. `suffixWeftPrimaryBranch`'s own adopt-pattern never hardcodes a name for exactly this reason — a hub whose host default branch is `master`/`trunk`/anything else must still reserve *that* branch's unsuffixed name for `_board`, not literally "main".
- **Correction (caught in discussion review r4 — a citation error in an earlier fix):** `suffixWeftPrimaryBranch(weftPath string)` (`internal/fabricengine/clone.go`) reads the checked-out branch via `git branch --show-current` at `weftPath` — the **weft** clone, immediately after `cloneRepo`, before the rename — never the host worktree; an earlier draft of this section wrongly attributed it to the host side. `CloneHub` also currently **discards** `suffixWeftPrimaryBranch`'s return value entirely (it only checks the error), so there is nothing to "reuse" as originally stated. Concrete fix: change `suffixWeftPrimaryBranch`'s signature to `(hostBranch string, err error)`, returning the branch name it already reads before renaming it — `CloneHub` captures that return value and passes it forward to `_board`'s own worktree-add call, which runs immediately afterward in the same function. No independent re-read is introduced or needed; re-reading at that point would incorrectly see `<hostBranch>-weft` (the rename already happened), which is exactly why threading the captured value through is required rather than optional.
- Fresh-bootstrap edge case (genuinely new hub, empty weft remote): after `suffixWeftPrimaryBranch` runs, HEAD moves onto `<hostBranch>-weft` *before* `<hostBranch>` ever received a commit — on a truly empty weft remote, `<hostBranch>` never becomes a real branch ref at all (an unborn HEAD has no underlying ref, just a symbolic HEAD target name). `git worktree add <path> <hostBranch>` would fail in this case. Resolution: when no `origin/<hostBranch>` exists, create `_board`'s branch as a fresh **orphan** — no shared history with `<hostBranch>-weft` or anything else. This matches board's current real-world property of being an entirely independent git history, just now co-located in the same repo/remote instead of a separate clone, rather than accidentally forking board's first commit off of whatever prime's weft content happens to be.
- Orphan-branch mechanism: `git worktree add --orphan <branch> <path>` (a single command, git ≥2.42) — not a hand-rolled `--detach` + `checkout --orphan` + working-tree-clear fallback, which is fragile (has to correctly clear a borrowed working tree left over from the detach start point) for no benefit on a greenfield tool. This **raises the repo's stated minimum git version** — `README.md`'s "Requirements" section currently says "Git 2.35+ (for `git worktree`)" and needs bumping to 2.42+ in the same commit. Sited in a **new file** (e.g. `internal/fabricengine/boardweft.go`), not `weftwiring.go` — that file's own header comment states every branch argument it handles "is ALWAYS a concrete, already-suffixed weft branch name" and that "this file never derives a branch name itself," both of which `_board`'s deliberately-unsuffixed `main` branch would falsify if the new worktree-add logic were added there instead.
- Rationale: minimal-diff reuse of an already-reserved geometry token (`hubgeometry.IsReservedHubName` already lists `BoardDirName`); reuses `weftwiring.go`'s existing `createWeftWorktree`-style primitives; the resulting behavior for board's own read/write path (`Config.Path = hubgeometry.BoardDir(hub)`) is byte-for-byte unchanged from today.
- Rejected: a differently-named directory for `weft:main`, leaving `_board`'s current meaning untouched (adds churn — a new geometry token, a new `IsReservedHubName` entry, a new hubgeometry accessor pair — for no behavioral benefit; `_board` already means "where board lives").

### No portal/junction mechanism needed

- Decision: non-prime worktrees continue to reach `_board` exactly as they do today — direct, unchanged `hubgeometry.BoardDir(layout.Hub)` path resolution from `boardcli`'s `PersistentPreRunE`. No new junction, no reuse of the slug-keyed `_portals/<slug>` mechanism.
- Rationale (discovered during exploration, corrects an earlier misreading of the source design doc's "portal" language): `BoardDir(hub) = filepath.Join(hub, BoardDirName)` is a pure function of `Hub`, and every worktree resolves to the *same* `Hub` value (`filepath.Dir(WorktreeRoot)` — the shared parent directory of all sibling worktrees). This is fundamentally different from `_lyx`/`_pattern`, which are per-worktree junctions addressed *inside* each worktree's own directory tree (`<worktree>/<RelPath>/_lyx`) and therefore genuinely need a junction to appear local. `_board` has never needed that — it's already a plain hub-level sibling directory, reachable via an ordinary absolute/hub-relative path from any worktree's Go process, with or without a junction. This holds identically whether `_board` is populated by a separate clone (today) or a second `git worktree add` of the weft repo (this task) — the physical directory's addressability doesn't change.

### `notes.json` reuses `tasks.json`'s exact schema — no separate shape, no `curated` flag

- Decision: `notes.json` stores the identical `Task` struct/JSON shape as `tasks.json` (`id, slug, title, depends_on, isolated, deferred, brief, body, status, short_name`), via a second instance of the same `Store` type pointed at a different file. There is no `curated` flag and no raw/curated two-tier distinction inside `notes.json` — an entry is either in `notes.json` (not yet claimable) or `tasks.json` (claimable); the move between them *is* the act of curation.
- Rationale: the original design doc's four-category model (Proposals → Manifest → Tasks → Done, with a `curated` promotion flag inside one loose file) added a distinction whose entire purpose was gating an LLM curation workflow — and that workflow is explicitly deferred to a follow-up task (see Scope/Out). Reusing `Task`'s exact shape means every piece of existing `Store` machinery (`Load`/`Save`, `UpsertTask`/`ApplyPatch`/`NewTask`, dangling-dependency/isolated/deferred/cycle validation, `MergeTasks`, `ListTasksBrief`/`ListTasksFull`) works unmodified against `notes.json` — it is a second file, not new engine code. This directly enables the next decision.
- This repo's own `manifest/` directory (`roadmap.md`'s Planned list + `designs/*.md`) is the lived reference model the user pointed to: Planned-list bullet-plus-linked-doc ≈ `tasks.json` entry with a `body`-backed design-file link; Someday's looser entries ≈ `notes.json`. Not a coincidence — the design doc already notes `manifest/roadmap.md`'s Planned list has board's Tasks-category shape today.
- Rejected: a distinct, narrower `notes.json` schema (`{id, slug, title, text, source, curated, status}`) proposed earlier in discussion — rejected by the user specifically because it would require field-remapping logic (and by extension LLM judgment) to promote an entry, defeating the point.

### `promote-note` — pure mechanical cross-store move

- Decision: a new CLI command (`lyx board promote-note`, exact name to be finalized in planning) atomically: upserts the note's fields into `tasks.json`, then removes the entry from `notes.json`. No field transformation. Requires new plumbing — this is genuinely new code (a cross-store atomic operation), not a reuse of today's single-store `MergeTasks`, which only knows about one file.
- Cross-file atomicity: `state.WriteJSON` (`internal/state/state.go`) is atomic **per file only** (rename-based); there is no cross-file transaction primitive anywhere in this codebase, so a crash between the two files' saves is a real, must-address risk. Resolution: save order is **upsert into `tasks.json` first, then remove from `notes.json` second** — duplicate-on-crash is deliberately preferred over loss-on-crash. A crash between the two saves leaves the entry present in *both* files (recoverable, never silently lost), not absent from both. Recovery is a plain retry of the same `promote-note` call.
- **Reconciling with global slug uniqueness (a real contradiction in an earlier draft, caught by discussion review r3):** the generic cross-store uniqueness gate (see below) would reject `promote-note`'s own internal `tasks.json` upsert on retry, since by design the slug is briefly present in *both* stores during/after a crash — the opposite of what every ordinary upsert must reject. `promote-note`'s internal upsert therefore explicitly **bypasses** the generic cross-store pre-check (it is the one legitimate path where transient dual-presence is expected), and retry logic treats an already-present, field-identical `tasks.json` entry as success rather than an error, then proceeds to (idempotently) remove from `notes.json`. No `RemoveTask`-side idempotency handling is needed beyond this: because removal is always the second/last step, a crash can only ever land *before* it runs, never after — there is no window where `notes.json`'s removal succeeds while `tasks.json`'s upsert is still unwritten.
- **Cross-store `depends_on` on promotion:** deliberately requires **no new validation code**. `depends_on` stays per-store-scoped (see the uniqueness decision below), so promoting a note whose `depends_on` still names another `notes.json`-only entry hits `Store.validateWrite`'s existing dangling-dependency check during the `tasks.json` upsert step — surfacing as an ordinary "dangling dependency" error. This is the intended behavior, not a gap to patch: promoting a note requires promoting its dependencies first, exactly as extending a dependency chain in `tasks.json` already requires today.
- Locking consequence: `Board`'s facade needs to become dual-store-aware. Recommend a single combined write lock (rename today's per-store `tasks.json.lock` concept to one `board.lock` guarding mutations to *either* file) rather than two separate per-file locks with an ordering rule — simpler, and removes deadlock risk entirely between a `promote-note` call and an ordinary `notes` or task upsert. `RenderToDisk`/README rendering reads both stores, so any write to *either* file should trigger a full README.md re-render (both the Tasks/Done and Manifest sections live on one page).
- Today's `pushLockFile` (`"tasks.json.push.lock"`) renames consistently to `board.push.lock` and is **kept**, not dropped — this is already today's existing double-lock pattern (board's own coarse outer push lock wrapping `PushCoalesced`'s finer-grained internal `.gitrepo-push.lock`), unchanged by this task; `PushWeftAt`'s delegation to `PushCoalesced` does not replace board's own outer lock, it composes with it exactly as it does today.
- At the git layer this needs no special handling: `_board`'s worktree holds `tasks.json`, `notes.json`, `README.md`, and lock files as sibling files at one worktree root, and `CommitWeftAt`'s wildcard-stage (`StageAllAndCommit`) already captures changes to both files in one commit regardless of which one changed — atomicity at the git level is free; only the in-process Go lock needs the new combined-lock design.

### Global slug uniqueness + length cap

- Decision: slug uniqueness is enforced across `tasks.json` and `notes.json` combined (an upsert into either store checks both stores' slug indices), and every slug is capped at **32 characters**, enforced at the shared `validateUpsertFields`/`NewTask`/`ApplyPatch` chokepoint (applies identically to both stores, since they share the code).
- Rationale: slugs seed lyx worktree directory names (`<hub>/<slug>`, `<hub>/<slug>-weft`, `<hub>/_portals/<RelPath>/<slug>`, `<hub>/_launchers/...`), which risk Windows `MAX_PATH` (260 char) problems if unbounded — no length limit exists anywhere in the codebase today. 32 was chosen (over an initially-proposed 50) to comfortably fit real slugs already used in this repo (`board`, `pattern-wiring`, `fabric-unified-view`, `codeintel-v1`) while giving a firmer path-length margin. Global (not per-file) uniqueness avoids a promote-time collision and keeps design-file naming (`design-<slug>.md`) unambiguous regardless of which store an entry currently lives in.
- Access mechanism for global uniqueness: lives at the `Board` facade level, not inside `Store` itself. `Store`'s existing `validateWrite`/`slugIndex` stay scoped to their own single file — no sibling-store reference is added to `Store`, which would complicate its already-simple, independently-testable single-file abstraction. Instead, `Board` (which already becomes dual-store-aware for the `promote-note` primitive — see below) performs a cross-store slug-availability pre-check, under the combined lock, before delegating an upsert to either `Store`'s own `UpsertTask`. `depends_on` validation is explicitly **not** made cross-store: it stays exactly as `Store.validateWrite` already implements it, scoped to each store's own snapshot — a `notes.json` entry may only `depends_on` other `notes.json` entries, a `tasks.json` entry only other `tasks.json` entries. Only slug identity is global; the dependency graph is not.

### `short_name` field

- Decision: add an optional `short_name` string field to `Task` (shared by both stores). No validation/length cap (display-only, not a path component). Falls back to `slug` when absent or empty.
- Rationale: mirrors an existing, working precedent one layer up — `mill-config.yaml`'s `repo.short_name` ("LYX") is exactly what builds today's VS Code `window.title: "LYX: board"` (mill's own `_vscode.py`, reusing the mill task's slug directly as the display label since mill has no separate per-task short-name concept). The user wants board v2's own tasks to have that same separation available once lyx grows its own worktree-spawn tooling — a longer, path-safe `slug` for the filesystem/branch identity, and a separate, friendlier `short_name` for display. This task only adds and round-trips the field; the consumer that would set a VS Code title from it is future `loom`/`fabricengine worktree add` work, out of scope here.

### Rendering: single `README.md`, renamed config keys, no sidebar

- Decision: `board.yaml`'s config keys change from `home`/`sidebar`/`proposal_prefix` to `readme` (default `README.md`, env `LYX_README`) and `design_prefix` (default `design-`, env `LYX_DESIGN_PREFIX`); `sidebar` is removed entirely (no more `_Sidebar.md`).
- Caveat on the "GitHub renders README.md directly" framing: GitHub auto-renders a repo's README only on its **default branch** — nothing in this task's design changes the weft remote's GitHub-level default-branch setting, so this benefit holds only as long as that setting is (or stays) `main`, which is outside lyx's control. Don't lean on that as the load-bearing justification for dropping the sidebar: the real justification is that `README.md` is self-navigating (one page, no separate nav file needed) — the GitHub auto-render is a nice-to-have on top when the default branch happens to be `main`, not the reason the sidebar goes away.
- The per-entry long-body detail-file pattern (today's `proposal-<slug>.md`, renders `Task.Body` verbatim when non-empty) stays, renamed to `design-<slug>.md`, and applies uniformly to entries in *either* store (any non-empty `Body`, whether the entry currently lives in `tasks.json` or `notes.json`).
- `README.md`'s Tasks/Done sections render from `tasks.json` via the existing bucket/layer logic (`ComputeLayers`, `renderHome`-equivalent), unchanged from today's behavior. The Manifest section renders from `notes.json` — recommend a flatter presentation (no bucket/layer grouping) since `notes.json` entries are loose, not-yet-scheduled ideas, even though the underlying engine could technically compute layers for them too; exact presentation is an implementation call for planning, not a blocking decision here.
- `notes.json`'s filename itself is not config-driven, matching `tasks.json`'s existing precedent (a hardcoded literal, not a config key).

### CLI verb surface

- Decision: existing top-level task verbs (`upsert`, `upsert-batch`, `set-status`, `remove`, `get`, `list`, `list-full`, `merge`, `set-deps`) keep their exact names and behavior, now operating on `tasks.json` inside `_board`. - **Q:** How should board's writes reach weft git, given the Weft Git Invariant's "no raw git against a weft worktree" rule? **A:** Keep board's existing detached-sync architecture (both commit and push happen in the detached child, never blocking the caller) exactly as today, but retarget its git calls through `internal/fabricengine` instead of raw `internal/gitrepo`. Confirmed as "exactly like the board module does it today, just now going to weft:main" — led to discovering `Fabric.CommitWeft` can't be reused directly (Warp-SHA trailer doesn't apply) and designing a new `CommitWeftAt` primitive alongside the existing `PushWeftAt`.
- **Q:** How do non-prime worktrees reach `_board`? **A:** They already do, with no portal/junction needed — `hubgeometry.BoardDir(layout.Hub)` is a pure function of the shared `Hub` path, unlike `_lyx`/`_pattern`'s per-worktree junctions. Corrects an over-complication in the original framing of this question.
- **Q:** Does this task build the GitHub-issue-intake/curation-triage automation? **A:** No — storage/rendering/CRUD only; the automation is explicitly deferred to a clearly-recorded follow-up task (new roadmap entry required in this task's own commit).
