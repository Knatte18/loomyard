## Findings (severity-ranked)

### F1 — MEDIUM — DoneChecks reads resolve status through a fail-open boolean (sibling of R9-6)
- **Where:** `internal/planglyph/donecheck.go:149` (`resolved := r.Status == quarry.StatusFound || r.Status == quarry.StatusMultipart`) and the four arms below it.
- **Scenario:** `doneCheckVerdicts` folds every non-found/non-multipart answer into "not resolved". For `create-not-done` and `rename-not-done-new` that fails closed (finding fires). For **`delete-not-done` and `rename-not-done-old` it fails OPEN**: a pre-resolution rejection (Status "", Error/Reason set), a `StatusAmbiguous` answer (candidates with that name STILL EXIST — the deletion/rename demonstrably did not fully land), or any future status outside quarry's four-value vocabulary all read as "the target is gone", and the blocking done-check passes. R9-6 established exactly this disposition for the same Status field's other two consumers (statusFindings, createFindings): an answer the policy has not been taught to read must fail closed, not slot into whichever boolean bucket it happens to land in. This is the last unswitched Status consumer in the package.
- **Severity rationale:** reachability today needs an ambiguous answer (real: a delete that removed one of two same-named declarations) or a mid-run plan edit / vocabulary widening; the ambiguous case is a genuine normal-flow false "done".
- **Fix:** classify each answer three ways — exists (found/multipart), gone (not_found), unreadable (anything else). `delete-not-done`/`rename-not-done-old` fire on exists AND on ambiguous (name still resolvable to something); unreadable answers produce a blocking `glyph-rejected` finding (the package's established fail-closed arm, rendered via `unreadableStatusDetail`) for every entry regardless of check ID. Add unit tests for rejection, ambiguous, and unknown-status answers on all four check IDs. **CONFIRMED** (by code reading + quarry's documented Status contract).

### F2 — MEDIUM — resolveTargets has no answer-coverage guard; an incomplete batched Resolve answer fails open across four consumers (sibling of R5-6 / the quarry.Name length guard)
- **Where:** `internal/planglyph/repo.go:88` (`resolveTargets`).
- **Scenario:** `statusFindings`, `resolveContainment`, and DetectDrift's post-repair revalidation all iterate the RESULTS slice, and `createFindings` looks results up by key with a silent `continue` on a miss — so if `(*quarry.Repo).Resolve` ever answers fewer results than targets (the positional contract breaking at a boundary this package cannot see inside), every uncovered target is silently exempted from the entire resolve-backed validation pass and the plan reads cleaner than it is. The package has already accepted this exact argument twice, for the two OTHER batched quarry boundaries: `CanonicalizeHandles` guards `quarry.Name`'s length ("a batched boundary this file cannot see inside is exactly where a length guard belongs", handle.go:211), and `doneCheckVerdicts` errors on a missing per-key answer (R5-6). The package's single Resolve chokepoint has neither guard.
- **Fix:** in `resolveTargets`, return an `ErrQuarryUnavailable`-wrapped error when `len(results) != len(targets)` — one seam, covers every consumer including DoneChecks and DetectDrift. Unit-testable only indirectly (real repos always satisfy the contract), so pin it with a direct test of the guard via a doc-level assertion or exported-for-test seam; at minimum the guard itself plus a comment. **PLAUSIBLE** (requires a quarry contract breach — same standing as the two guards already shipped).

### F3 — MEDIUM — createHandleResults silently drops a handle whose expected glyph got no answer; the Create inversion then silently passes for it (sibling of R5-6)
- **Where:** `internal/planglyph/create.go:93-99` (`if r, ok := byGlyph[key]; ok`), consumed by `createFindings`' `if !ok { continue }` at create.go:130-133.
- **Scenario:** `createHandleResults` builds its own target list — every key in it was put there by the function itself — yet a key missing from the answer index is dropped without a word, and `createFindings` cannot distinguish that from "a path or bare symbol collectGlyphTargets legitimately excluded", so the handle's Create inversion is skipped entirely: no create-already-exists possible, no create-new-unit, no glyph-rejected. Under the inversion, silence means "does not exist yet, carry on". This is byte-for-byte the R5-6 argument, which doneCheckVerdicts already implements for its identical situation (donecheck.go:140-148).
- **Fix:** after building `byHandle`, error with `ErrQuarryUnavailable` naming the handle when any `expected` key lacks an answer, mirroring doneCheckVerdicts' guard. Add a unit test through `createHandleResults`' seam if reachable hermetically, else through the guard split pattern donecheck.go already established. **PLAUSIBLE** (same reachability class as F2; F2's length guard narrows it to the echo-mismatch case, this closes it).

### F4 — MEDIUM — package-self vs file-self overlap is invisible to BOTH containment tiers
- **Where:** `internal/planparser/containment.go:26-74` (syntacticContainment: member-vs-self only) and `internal/planglyph/containment.go:63-151` (resolveContainment: member-vs-file only).
- **Scenario:** card A targets the whole-package unit self glyph `internal/foo#` (a legal target — checkProsaSymbolTarget explicitly admits it as the whole-package spelling, and nothing forbids it on an Edit group); card B targets the file self glyph `internal/foo/bar.go#`. Both refs are SELF glyphs, so the syntactic tier never compares them (it pairs members against selves only) and the resolve tier never compares them (it pairs resolved member files against selves only). websterengine.deriveEdges matches by exact string. Result: no edge, blind parallel dispatch on physically overlapping targets — the precise hazard the two-tier containment design exists to close ("no DAG edge, blind parallel dispatch, merge conflict", manifest/designs/quarry-glyph-plan-alphabet.md). Live-confirmed both spellings resolve found (`internal/planglyph#` → found/Listing; file self glyphs → found).
- **Fix:** extend syntacticContainment (the overlap is fully lexical): for every pair of self glyphs on DIFFERENT cards, where one glyph's `UnitPath()` carries a file extension and the other's does not, report `containment-unit-overlap` when `path.Dir(fileUnitPath) == packageUnitPath` — a unit's files are its direct children, so parent-directory equality is exact for Go. Uses `Glyph.UnitPath()` (the one allowed glyph→path call) — never raw string surgery on the ref. Update the check's row in `contracts/specs/loom-plan-spec.md` and the tier description in the design doc in the same change. **CONFIRMED** (by construction; hermetic test will demonstrate).

### F5 — LOW — checkRenamePairShape admits the (self-glyph Old → handle New) pair; it is refused only later, with a false detail (sibling of R9-2)
- **Where:** `internal/planparser/validate.go:760-797` (checkRenamePairShape), `internal/planglyph/handle.go:116-124` (renameDeclSource's first arm).
- **Scenario:** the format admits exactly two pair shapes (spec §"Plan: handles", line 228): symbol rename = member-glyph Old → handle New; file rename = self Old → self New. The pair `internal/foo/bar.go#` → `plan:internal/foo#NewName` is NEITHER, yet passes both negation checks: Old classifies refKindGlyph (rename-from-not-glyph silent), New classifies refKindHandle (rename-to-not-handle silent), and isFileRenamePair declines (New not a glyph) without consequence. It is caught only inside resolvePass: a found SELF glyph carries `Listing` and NO `Symbols` (live-confirmed against quarry v0.1.0), so renameDeclSource's `len(r.Symbols) == 0` arm fires `rename-old-unresolved` — blocking, good — but its detail says the old side "did not resolve found", which is FALSE (it resolved found), sending the operator hunting a resolution problem instead of a shape problem.
- **Fix:** two halves. (a) Pure layer: in checkRenamePairShape, a non-file pair whose New side is a handle and whose Old side parses as a SELF glyph gets a `rename-from-not-glyph` finding with a shape-accurate detail (a symbol rename's old side must name a symbol — a member glyph — not a file/unit self glyph). (b) renameDeclSource: split the found-with-no-Symbols case out of the not-found case so the detail states what actually happened. Spec row 18's wording updated in the same change. **CONFIRMED** (live probe).

### F6 — LOW — CanonicalizeHandles rewrites the plan on disk by silent last-wins when ONE draft handle canonicalizes to TWO glyphs (residue of R9-3)
- **Where:** `internal/planglyph/handle.go:246-272` (`subs[owners[0]] = canonical` under the sorted-canonicals loop).
- **Scenario:** the same draft handle claimed by two declaring sources (Create declaration + Rename to-side, or two Rename to-sides — R9-3's exact plans) produces two declSources, two Name answers, and potentially two DIFFERENT canonicals c1 ≠ c2 each owned by the one draft. The guard covers the inverse only (N drafts → 1 canonical, handle-canonical-collision); here `subs[draft]` is assigned once per canonical, last-wins over sort order, and `RewriteRefs` then mutates every card file to the arbitrarily-chosen canonical BEFORE the composite report — which does, provably, always carry the blocking pure `handle-collision` finding (every multi-source claim configuration is a claim collision since R9-3) — is ever rendered. The plan is blocked either way; the defect is that a gate mutates the artifact non-deterministically under an already-fatal condition, leaving a stale arbitrary spelling for the operator to untangle after fixing the collision.
- **Fix:** group canonicals per draft handle first; a draft owning more than one canonical contributes NO substitution (comment: the pure handle-collision finding owns this plan's refusal). Test: such a plan's card files stay byte-identical through CanonicalizeHandles. **CONFIRMED** (by code reading; every trigger is also a handle-collision plan).

### F7 — LOW — classify.go rule 4's comment promises a root:-scoped behaviour that directory-target then refuses; the finding's remedy text omits the file case
- **Where:** `internal/planparser/classify.go:51-55` (rule 4's closing paragraph), `internal/planparser/validate.go:469-477` (directory-target detail).
- **Scenario:** under `root: internal/foo`, a bare `Makefile` normalizes to `internal/foo/Makefile` — which classify.go's comment calls "the intended behaviour — a bare filename under a declared root: means the file in that root". But that ref is slashed and extensionless, so canonicalizablePath declines it and checkDirectoryTarget then flags it as "names a directory with no file extension" — a blocking refusal of the very spelling the comment blesses, with a detail whose remedy speaks only of packages. The refusal itself is the right disposition (a lexical classifier cannot tell `internal/foo/Makefile` the file from a directory, and the legal spelling exists: the repository-root-relative file self glyph `internal/foo/Makefile#`, live-confirmed to resolve found via `plugins/.../bin/gh#`). What is wrong is the two texts: the comment overpromises, and the finding's detail under-advises.
- **Fix:** correct rule 4's comment (a bare extensionless filename is a REPOSITORY-ROOT spelling; under a non-"." root: the joined form is refused by directory-target and the file self glyph is the legal spelling), and extend directory-target's detail to offer the file-self-glyph remedy for an extensionless file alongside the unit-glyph remedy for a package. Spec line 150 already scopes the rule to repository-root filenames — add the root:-interaction sentence there. Doc/detail change only; no classification behaviour changes. **CONFIRMED** (live probe of the glyph spelling).
