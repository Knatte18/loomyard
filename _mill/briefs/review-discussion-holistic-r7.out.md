### [BLOCKING:design] reed-rename rests on a false claim about the doc comment

**Issue:** The document states: *"Additional fix in the same commit: `internal/reedengine/headertemplate.go`'s doc comment claims the asset is rendered "via internal/stencil", which is false — `header.go` uses `tokenvocab`."* That premise is verifiably false. `internal/tokenvocab/render.go:12` is `return stencil.Fill(template, Build(c))`, and `internal/reedengine/header.go:17` calls `tokenvocab.Render`. **Fix:** In `### reed-rename`, delete the bullet quoted above verbatim and replace it with:

> - Additional fix in the same commit: `internal/reedengine/headertemplate.go`'s doc comment (`headertemplate.go:2-4`) names the asset by its old filename `header-template.md` and describes the `*-template.md` naming convention that this rename retires for this file. Rewrite it to name `console-header.md` and to state the render path precisely — `tokenvocab.Render` (`internal/tokenvocab/render.go:12`), which is itself a thin wrapper over `stencil.Fill`. The existing "rendered via internal/stencil" wording is not false and must not be "corrected" to say otherwise.

Knock-on edits in the same document: (a) `## Scope` → **In**, the bullet *"Renaming `internal/reedengine/header-template.md` to `console-header.md` and fixing that file's stale doc comment"* — change "fixing that file's stale doc comment" to "updating that asset's doc comment and its own leading banner (`header-template.md:1`) for the new filename"; (b) `## Q&A log`, the entry *"Q: Does reed's file stay in `internal/reedengine`?"* — no change needed, it makes no correctness claim; (c) no change to `## Out`, whose wording ("rendered through `internal/tokenvocab`") is accurate. Options were: keep the "is false" claim (rejected — it is refuted by `internal/tokenvocab/render.go:12`), or drop the doc-comment fix entirely (rejected — the comment still hardcodes the pre-rename filename, so it does need an edit). Recommend the replacement above.

### [BLOCKING:decision] `-dev` build's disposition for the reconciliation row is unstated

**Section:** `### seeding-trigger` (the `-dev` bullet), against `### stamp-format-and-edit-detection` and `## Testing`.
**Issue:** The rule is stated as *"a `-dev` build performs row 1 of the edit-detection table (seed when absent) and skips row 2 (refresh when untouched)"*. Rows 3 (the reconciliation restamp), 4, and 5 have no stated disposition under `-dev`. Row 3 is load-bearing exactly in the dev loop: `## Testing` → **Port-back guard** asserts *"promote, then re-seed from the new default, and assert the board copy ends up restamped and back in the untouched state via the reconciliation row"*, and `### seeding-trigger` itself says *"the dev binary is the one used in the prescribed test-live loop"*. If a `-dev` build skips row 3, that assertion is unreachable in the loop it was written for, and the board copy stays classified edited forever — the precise failure row 3 exists to prevent.
**Fix:** In `### seeding-trigger`, after the sentence *"A production build performs the full table."*, insert:

> Only row 2 is skipped. A `-dev` build performs rows 1, 3, 4 and 5 unchanged — in particular the reconciliation restamp (row 3), which is what returns a board copy to the untouched state after a `promote`, the one loop the dev binary is built for. Row 3 cannot reintroduce the thrash it is grouped with: it writes only the stamp line inside the leading banner, which is excluded from the hash by construction, and it fires only when the body already equals *that* binary's shipped default, so the two binaries can never restamp the same file in opposite directions on alternating runs.

Options considered: (a) dev skips rows 2 and 3 — rejected, it breaks the promote round trip the `port-back-is-mechanical-not-remembered` decision is built on; (b) dev skips row 2 only — recommended, and safe because the hash is taken over the body after the leading comment block is stripped (`### stamp-format-and-edit-detection`, first bullet), matching `internal/stencil/stencil.go:67`'s `stripLeadingComment`, so a restamp is invisible to every subsequent classification. Knock-on edits: `## Testing` → **Dev/prod seeding** gains a third assertion — *"Assert that a `-dev` build still performs the reconciliation row: a board copy whose body equals the dev binary's shipped default but whose stamp names an older one is restamped and reclassified untouched."*; `## Q&A log`, the entry *"A: A `-dev` build seeds absent files but never refreshes untouched ones, warning instead."* gains *"Only the refresh row is skipped; the reconciliation restamp still runs."*

### [BLOCKING:consistency] `Reconcile`'s stated signature contradicts two later sections

**Section:** `### seeding-trigger` vs. `### seeding-trigger` (dev bullet), `### port-back-is-mechanical-not-remembered`, and `## Testing`.
**Issue:** `### seeding-trigger` declares *"a `Reconcile(baseDir, registry)` pass applies the edit-detection table and returns the list of paths it actually wrote"*. Twenty lines later the same decision says *"The composition root threads the resulting mode into `stencilstore.Reconcile` as an explicit argument"*, and `## Testing` → **Dev/prod seeding** says *"The assertions drive `Reconcile`'s explicit mode argument"* — a third parameter the declared two-argument signature does not have. A fourth input is never given a home at all: `### port-back-is-mechanical-not-remembered` puts the drift warning in *"the same pass over the files that the drift check already uses"*, which requires the worktree's `stencils/` source path, and says it must be *"skipped silently"* where that tree is absent. The superseded two-arg spelling is the kind of stale statement a plan writer will implement literally.
**Fix:** In `### seeding-trigger`, replace *"a `Reconcile(baseDir, registry)` pass applies the edit-detection table and returns the list of paths it actually wrote"* with:

> a `Reconcile(baseDir string, registry Registry, mode Mode, sourceDir string) ([]string, error)` pass applies the edit-detection table and returns the list of paths it actually wrote. `mode` is the caller-supplied dev/production build channel (see the `-dev` bullet below); `sourceDir` is the worktree's `stencils/` tree for the drift comparison, and the empty string means "no source tree here", which is what makes the warning silent in a consumer repo. Both are arguments, never values `stencilstore` derives, which is what keeps its tests hermetic against a bare `t.TempDir()`.

Knock-on edits: `### stencilstore-ownership` — the sentence *"Its API takes an explicit base directory from the caller, e.g. `stencilstore.Read(baseDir, "loom-template-discussion")`"* should gain *"; `Reconcile` additionally takes the registry, the build mode, and the optional worktree source directory — see `seeding-trigger` for the full signature"*, so the two decisions state one API. `### port-back-is-mechanical-not-remembered` — the phrase *"the same warning channel and the same pass over the files that the drift check already uses"* should read *"…the same `Reconcile` pass, which receives the worktree `stencils/` path as its `sourceDir` argument"*. `## Testing` → **Trigger site** should add the empty-`sourceDir` case to its existing skip assertion. Options: keep the drift comparison out of `Reconcile` as a separate `stencilstore.Drift(baseDir, sourceDir)` call (rejected — `### port-back…` explicitly justifies the design on the 0.15 ms cost of *one* pass over the files, and two passes would double the read it measured), versus folding it into `Reconcile` (recommended, matches the stated rationale).

### [NIT:consistency] "internal/gitrepo performs no CRLF conversion" misreads its own doc

**Section:** `### stamp-format-and-edit-detection`, the LF-normalisation bullet.
**Issue:** The text reads *"since `internal/gitrepo` performs no CRLF conversion (`internal/gitrepo/doc.go:218`)"*. That line says *go-git* performs none, and the same paragraph's conclusion is the opposite of the one drawn here: *"This is why StageAndCommit and StageAllAndCommit stay CLI-bound"* — i.e. `internal/gitrepo`'s commit path deliberately routes through CLI git precisely so that CRLF conversion **does** happen. The conclusion (normalise both sides) survives, but the stated reason is backwards and would mislead a plan writer into thinking `gitrepo` is conversion-free end to end.
**Fix:** Replace the quoted clause with:

> since the `diff <name>` base is read through go-git, which performs no CRLF conversion at all (`internal/gitrepo/doc.go:218`), while the working-tree copy it is compared against was written by CLI git, which does — the two sides can differ by line ending alone, so both must be LF-normalised before hashing or diffing.

Knock-on edit: `## Q&A log`, the entry *"Q: What happens to the hashes on a machine with `core.autocrlf=true`?"* — append *"The base-recovery path needs the same normalisation for the opposite reason: go-git returns stored blob bytes untouched while the on-disk copy went through CLI git's conversion."* This also strengthens `## Testing` → **Hash normalisation**, which already names both paths and needs no change.
