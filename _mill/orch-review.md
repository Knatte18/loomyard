# Orchestrator review: stencils-directory-reorg discussion.md

Reviewed against what we actually designed in the originating conversation (directory layout, `<family>-<type>-<role>.md` naming, no junctions, immediate-effect runtime read, and — the operator's own later correction — a repo self-hosting `lyx` must be able to run local stencil overrides with fallback to shipped defaults) and against the current `main` codebase.

## Verdict

Sound, and the mechanism decided here is *better* than what was originally proposed — not a deviation from it. The task correctly discarded the junction-based layout the moment the spike disproved it, and the one-tree-plus-hash-stamp design satisfies the operator's override requirement with less machinery than the two-tree "default + override" shape I'd described verbally. One real, moderate-severity gap: the design's own prescribed fast-iteration loop for `loomyard`'s self-hosting case creates a silent, permanent-drift failure mode that nothing in Testing or the CLI surface catches mechanically.

## Finding: the design's own prescribed fast-iteration loop has no mechanical guard against silent, permanent drift

The `deployment-versus-production` decision prescribes the loomyard development loop as: **edit the board copy directly (immediate effect, no rebuild) → test live → port the change back into `stencils/` by hand → redeploy to make it permanent.** That hand-port-back step is exactly the kind of manual synchronization step this project otherwise refuses to trust — CONSTRAINTS.md is full of machine guards precisely because "review discipline" alone was judged insufficient elsewhere in this same codebase (the Fabric Destruction Chokepoint Invariant, the Mutation Record Invariant, and this very task's own treadle-allowlist and enforcement-walk amendments all exist for that reason).

Concretely, what happens if a developer edits the board copy, tests it, is satisfied, and forgets to port the change back before committing elsewhere:

1. The board copy's hash no longer matches its stamp (it was legitimately edited) — so per `stamp-format-and-edit-detection`'s own table, it is now permanently in the "human-edited → never touched" state.
2. The change was never written to the committed `stencils/` source, so it does not exist in that tree's git history at all — only in `_board`'s own `weft:main` history, a separate, less-visible commit stream nobody reviewing `stencils/` would think to check.
3. Every future default refresh silently skips this file forever (by design — that's what "never touched" means), so the drift is not self-healing and not re-surfaced except via the passive, easy-to-miss `logger.Warn` on some *later*, unrelated default bump — and even then only as a notice, never a block.

The net effect: the one repo where this mechanism is exercised most often — `loomyard` itself, actively building this exact feature — has the weakest protection against a real edit becoming permanently invisible to its own source tree. Nothing in **Testing** checks that `stencils/`'s committed content matches what `_board/_lyx/stencils/` actually has stamped for `loomyard`'s own hub; nothing in the **CLI surface** (`list`/`validate`/`diff`/`sync`) is described as a required pre-commit or CI step that would catch this before it lands. `lyx stencil diff <name>` exists and could catch it — but only if someone remembers to run it, which is the exact discipline-dependent failure mode the hash-stamp mechanism was built to remove for the general operator case.

Suggested fix, for the plan phase to weigh, not decided here: either (a) add a CI/build-time check asserting `stencils/`'s tree, once seeded, produces byte-identical stamps to what `loomyard`'s own `_board/_lyx/stencils/` currently has — catching an unported board-copy edit before it can be silently forgotten — or (b) note explicitly in the operator-facing docs that `lyx stencil diff --all` (or equivalent) is a required step before committing any `stencils/`-adjacent change in this repo specifically, and enforce it via a pre-commit hook rather than leaving it to memory.
