## Design read

**The central architectural move — extracting `Discussion-Validate`'s checks into a leaf package mirroring `internal/planparser`, then having both the `ShedProducer` row and a new CLI verb call the identical function — is the only design that actually satisfies the roadmap item's stated goal.** The roadmap's whole point was "the agent's self-check and the mechanical gate can never disagree," and the discussion is explicit that this is a correctness property, not a convenience: it backs the claim with its own `parity-tests-per-gate` decision (a test driving both the producer path and the CLI path over the same fixtures, asserting equal verdicts) rather than asserting the guarantee and hoping a future refactor doesn't fork the two call sites apart. That test is the one piece of engineering in this task that actually verifies the property the whole exercise exists for.

**`findings-not-bool` correctly identifies and closes the actual gap this task is solving.** The problem statement itself names the failure mode precisely: today's `Stuck` carries an empty `OutputPointer`, so a bounced-back writer has zero information about *what* it got wrong, only that it did. A `(bool, error)` extraction — technically simpler, and closer to a literal one-to-one port of the existing `Call` logic — would have shipped a standalone-callable check that still couldn't tell the self-checking agent anything useful, silently failing to solve the stated problem while looking done. Naming this as the rejected alternative, rather than not considering it, shows the discussion tracked back to the actual motivating problem rather than treating "extract the logic" as the whole task.

**`producer-contract-unchanged` shows real discipline against an easy, plausible-looking scope expansion.** It would be natural, while already touching this code, to widen `discussionValidate.Call`'s `OutputPointer` to carry the findings — the type is right there, `Stuck` currently wastes it. The discussion instead holds the line at "only the body changes," citing that this is governed by the Producer Pointer-Rule Invariant and that no consumer has asked for it. This mirrors the exact restraint pattern praised in this session's review of `loom: convert to a Shed recipe` (`landing-parity`: don't fix an adjacent thing just because you're standing next to it) — here applied preemptively rather than to an already-existing gap.

**`verbs-reuse-the-existing-prerun-wiring` makes a real, checkable claim rather than a hand-wave, and I independently confirmed its premise.** The decision's whole justification — that a lighter paths-only wiring path would be "two code paths over exactly the geometry this task is trying to single-source" — depends on `wire()` actually being cheap enough in this context to reuse wholesale. The discussion grounds this in loom being hub-only and the calling agent running mid-`loom`-run inside an already-fully-wired worktree, which is a specific, verifiable claim about *when* these verbs run, not just "it's simpler." Combined with `resolvePersistentPreRun`'s confirmed skip-on-bare-`loom` behavior, the reasoning holds together.

**The two-flat-verbs naming decision (`validate-discussion`/`validate-plan`, tracking `Discussion-Validate`/`Plan-Validate` one-to-one) is a small thing done for the right reason.** The stated rationale — "what makes the mapping obvious to an agent reading a prompt that names the row" — is the actual audience for this naming choice: not a human operator browsing `--help`, but the LLM-authored `Discussion-Write`/`Plan-Write` prompts (written in the *next* two tasks) that need to name these verbs unambiguously. Designing the CLI surface around its actual first-class caller, rather than around conventional CLI ergonomics, is the correct call given this task's own stated purpose.

**Scope discipline is notably strong given how much this task's own reasoning could have justified widening.** The clearest temptation avoided: `discussionparser-declares-no-paths` explicitly declines "full `planparser` parity" (moving `DiscussionDir`/`DecisionRecord`/`SupportLog` path declaration into the new package to match `planparser`'s `PlanDir`/`PlanOverview` shape), on the grounds that those three accessors take a `*lyxcwd.Location` a leaf package may not import, and reshaping them serves no caller this task has. Mirroring `planparser` was the whole naming rationale one section earlier — resisting the pull to mirror it *structurally* too, once doing so would require touching code with no consumer asking for it, is the harder discipline of the two. Also genuinely out, correctly: any change to `internal/planparser` itself (already the shared implementation, nothing to extract), `Plan-Sweep` (acknowledged as a future second consumer of the new package's section-parsing shape, but explicitly not built here), and any `loomcli.wire` refactor.

One thing worth flagging for the plan stage, not a defect: `envelope-and-exit-contract` collapses "gate failed with findings" and "I/O fault" onto the same exit code (1), distinguished only by envelope message text — reasonable given `internal/output`'s existing two-helper shape (`Err` vs `ErrFields`) offers no natural third state, but it does mean a shell script (as opposed to an agent reading the JSON body) checking only `$?` cannot distinguish "the discussion needs more work" from "something is broken." The discussion's own stated audience is an LLM agent reading the envelope, not a shell script branching on exit code alone, so this is very likely the right tradeoff — just worth the plan stage confirming that's still the only consumer anticipated, since it's the one place two genuinely different failure modes were deliberately given one exit code.
