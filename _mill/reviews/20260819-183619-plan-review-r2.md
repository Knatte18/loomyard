## Findings

### [BLOCKING:design] Origin-commit's KindCommitCreated omission is unjustified
**Location:** Overview Shared Decision `origin-record-carries-one-KindFileWritten-and-no-commit-record` (applies to batches 1, 2); implemented in Batch 1 Card 3 (`CommitWeftPaths` takes no `*Mutations`) and Batch 2 Card 5 (`Add`'s commit "sha/committed returns are deliberately discarded and no KindCommitCreated is appended").
**Issue:** `Add` will, for the first time, land a real commit on the weft branch, but the decision's rationale only defends the `KindFileWritten` entry's correctness against the live-state mutation oracle — it never addresses why omitting `KindCommitCreated` is safe. `KindCommitCreated` is structurally exempt from that oracle's commission check (`manifestObservableKind[KindCommitCreated] = false` in `livestate_mutationoracle_test.go`), so the oracle cannot validate this half of the decision at all, and Card 9's "verify against the real oracle" promise is vacuous for it. This also breaks with every existing precedent in the package: `commit.go` and `stencilcommit.go` both append `KindCommitCreated` at every commit success site. The result is `AddResult.Mutations` (surfaced verbatim in the CLI JSON envelope) silently under-reporting a real mutation, which is exactly what the Mutation Record Invariant exists to prevent ("so a consumer can tell 'no error was returned' apart from 'something was actually mutated' without parsing prose").
**Fix:** Either give `CommitWeftPaths` a `*Mutations` parameter and append `KindCommitCreated` on `committed == true` (matching `commit.go`'s pattern), or replace the decision's rationale with one that actually justifies the omission (e.g. cite the git-state-kind exemption directly rather than the unrelated `KindFileWritten` commission argument) and have Card 9 explicitly confirm the mutation oracle has no way to catch this gap rather than implying it does.

## Verdict

Fix the Add-commit mutation-record omission's rationale/behavior before implementation starts.
