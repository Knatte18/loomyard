## Findings

### [BLOCKING] Card 11 escalation lacks a deadline check between re-dial failure and kill+respawn
**Location:** batch 4 / Card 11
**Issue:** The escalation reuses step 6's fixed 10×50ms (~500ms) dial retry with no stated deadline check between "fresh dial+finalize also fails" and calling `proc.KillPID`+respawn. With `supervised_test.go`'s existing, unmodified `TestEnsureSupervised_UncontendedLockWithUndialableHealthyStateReturnsErrServerSpawnTimeout` (timeout=300ms, uncontended lock, a healthy-but-undialable state — exactly the trigger condition Card 11 describes), the ~500ms escalation cost alone exceeds the 300ms deadline before ever reaching a bail-out check, so the code would fall through to the real respawn step using the test's deliberately-nonexistent command `"lyx-codeintel-should-never-spawn"`, failing at `cmd.Start()` with a spawn error instead of `ErrServerSpawnTimeoutSentinel` — breaking this test, which Card 11 leaves in `Context:` (read-only), not `Edits:`.
**Fix:** Card 11 must explicitly require a `time.Now().After(deadline)` check immediately after `reconnectUnderLock` returns `healthy == false` and before `KillPID`/respawn (mirroring the existing step-2/step-3 deadline guards), and must call out that `supervised_test.go`'s uncontended-lock test now exercises the escalation path and needs re-verification (or an explicit edit) rather than being left implicitly unchanged.

### [BLOCKING] Card 4 Requirements reference `formatLocation` from a file absent from Context/Edits
**Location:** batch 2 / Card 4
**Issue:** Card 4's `Context:` is `lspclient.go, symbol.go, errors.go` and `Edits:` is `refs.go, doc.go` — neither lists `position.go`, yet the Requirements text directly names `formatLocation` (defined in `position.go`) for building `ErrAmbiguousSymbol` candidates, and separately relies on `lspRange`/`lspPosition`/`SelectionRange.Start` (also `position.go` types). Card 6 has the same gap (mentions `SelectionRange`/`lspPosition` with `position.go` absent from its Context too).
**Fix:** Add `internal/codeintelengine/position.go` to Card 4's (and Card 6's) `Context:` list.

### [NIT] `refs_test.go`'s stale call-chain comment after the supervised flip
**Location:** batch 4 / Card 12 (interacts with batch 2 / Card 6's `refs_test.go`)
**Issue:** `TestReferences_HasNativeDaemonRoutesThroughEnsureServer`'s doc comment in `refs_test.go` documents the pre-flip chain "`References -> lookup -> acquireConnection -> ensureServer -> ensureNative -> resolveGoToolchain -> the fake installer`". After Card 12, `ensureServer` calls `resolveGoToolchain` directly and only falls back to `ensureNative` on a *post*-toolchain-resolution `ensureSupervised` failure, so a toolchain-install failure (this test's scenario) no longer routes through `ensureNative` at all — the assertion still passes (errors.Is chain intact) but the comment becomes inaccurate. No card in batch 3/4 touches `refs_test.go`.
**Fix:** Add a one-line edit to this comment in Card 12 (or a follow-up note) so the documented call chain matches post-flip behavior, consistent with the plan's otherwise thorough "docs land in the same commit" discipline.

### [NIT] Batch 2's deferred `--in-file` integration coverage is not actually created anywhere in the plan
**Location:** batch 2 / Batch Tests
**Issue:** The Batch Tests section states integration coverage of `--in-file` against real gopls (the same-name-in-two-types ambiguity case) "is deferred to the out-of-band `-tags integration` suite... and is not part of this batch's gate," implying such coverage exists or will exist, but no card in batches 2–4 adds or edits an integration test file (e.g. `refs_integration_test.go`) for the `InFile` resolve path.
**Fix:** Reword to state this coverage is out of scope for this task (not merely gate-excluded), or add a card creating it if intended as a deliverable.
