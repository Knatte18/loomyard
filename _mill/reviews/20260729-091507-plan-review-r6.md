## Findings

### [BLOCKING] Batch mode ships with no CLI help-text update
**Location:** batch 10 / cards 39, 40 (definition/refs/symbol batch mode)
**Issue:** `cobra.MinimumNArgs(1)` replaces `ExactArgs(1)` and 2+ positional args now produce an entirely different top-level JSON shape (`"results"` array, a 4th `"error"` status, worst-outcome exit codes 0–3) — a major observable CLI behavior change — but no card updates `refsCommand`/`definitionCommand`/`symbolCommand`'s `Long` text to document it; only the package-level Go doc comment (card 44) gets the batch-mode prose. `lyx codeintel refs --help` still describes only the single-arg shape established in batch 9.
**Fix:** add a requirement to cards 39/40 appending a batch-mode example and JSON-shape sentence to each verb's `Long`, per CONSTRAINTS.md's CLI/Cobra Invariant ("stale help is a review-blocking defect" when behavior changes).

### [BLOCKING] Context completeness gaps recur across several cards
**Location:** cards 27, 30, 31, 33, 38
**Issue:** Requirements reference symbols whose defining file is absent from that card's `Context:`/`Edits:` list. Card 27 constructs `Options`/calls `References` (defined in `refs.go`, not listed). Card 30's `symbolFromClient` calls `DetectLanguage` (`detect.go`, not listed) and takes an `entry Entry` parameter (`registry.go`, not listed). Card 31's new test calls `Definition` directly (`definition.go`, not listed). Cards 33 and 38 build `emitLookupResult`/`classifyLookupError` around `codeintelengine.Reference` and `codeintelengine.SymbolMatch` (`refs.go`/`symbol.go`, neither listed). Per the source-grounding rule for plan review, a missing entry means cold-start exploration for the implementer.
**Fix:** add the missing files to each card's `Context:` — `refs.go` (27, 33, 38), `detect.go` + `registry.go` (30), `definition.go` (31).

### [NIT] `ensureSupervised`'s retry loop doesn't specify true-error handling
**Location:** batch 6 / card 24
**Issue:** the loop's requirements branch only on `TryAcquireWriteLock`'s bool result and `readDaemonState`'s presence/staleness; neither function's genuine `error` return (an OS-level failure distinct from "lock held by someone else" / "no state yet") has a stated handling path in the loop description.
**Fix:** add one sentence stating a non-nil error from either call aborts the loop immediately with the wrapped error, rather than being folded into the "not acquired" / "absent" branches.

## Verdict

REQUEST_CHANGES
Two BLOCKING gaps (stale batch-mode help text; several Context-completeness omissions) plus one NIT need fixing before approval.
