## Findings

### [BLOCKING:design] Standalone `run` panics on a failed integration suite instead of recording an unlocalized failure
**Location:** `internal/webstercli/run.go:57-70`
**Issue:** `runCmd`'s `RunE` unconditionally builds `OpenBisector: func() (websterengine.FabricBisector, error) { return c.openFabric() }`. In standalone mode `c.openFabric` is `nil` (`internal/webstercli/wiring.go:205`), so this wrapper closure is itself always non-nil — `runIntegrationStage`'s `if deps.OpenBisector == nil` guard (`internal/websterengine/runlevel.go:828`) never fires through the real CLI, and calling the closure invokes a nil `c.openFabric`, panicking. This contradicts card 27/28's explicit design ("a nil OpenBisector means 'no fabric in this mode'"), discussion.md line 129 ("the CLI supplies `RunDeps.OpenBisector` in hub mode and `nil` in standalone"), and the Shared Decision "no zero-value fallbacks on new told fields." Card 32's nil-bisector test (`runlevel_test.go`) and card 41's wiring test (`wiring_test.go`) both only check `c.openFabric` / `RunDeps.OpenBisector` in isolation — neither exercises `run.go`'s own Deps construction, so no test in the suite catches this.
**Fix:** In `runCmd`, only wrap `c.openFabric` into the `OpenBisector` closure when `c.openFabric != nil`; leave the field literally `nil` in standalone (e.g. `var ob func() (websterengine.FabricBisector, error); if c.openFabric != nil { ob = func() (...) { return c.openFabric() } }`, then `OpenBisector: ob`).

### [NIT:consistency] `--target-dir` absolute-path resolution happens in `wiring.go`, not at the flag-parsing CLI boundary
**Location:** `internal/webstercli/cli.go:184-189`, `internal/webstercli/wiring.go:225-233`
**Issue:** Card 34 says `--target-dir` "is resolved to an absolute path at this CLI boundary" (i.e. where the flag is declared), but the raw flag value is stored unresolved on `websterCLI` and only turned absolute later, inside `wireStandalone`/`resolveStandaloneTarget`.
**Fix:** Either reword card 34's requirement (documentation-only, since behaviour is correct) or note explicitly that "this CLI boundary" spans the pre-run's delegation into `wire`, to avoid a future reader assuming `cli.go` itself does the `filepath.Abs`.

## Verdict
