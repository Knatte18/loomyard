## Findings

### [BLOCKING] verify: never re-runs the Hub Geometry literal guard after render.go changes
**Location:** `00-overview.md`'s top-level `verify:` and batch 2's own `verify:`
**Issue:** `TestEnforcement_GeometryLiterals` (`internal/hubgeometry/enforcement_test.go`) is a repo-wide AST walk and the sole machine enforcement of "no other package may construct `_lyx`/`_pattern`/etc. in a path-construction context" — but it only executes when `go test` targets `./internal/hubgeometry/...` (or `./...`); running the walk from inside the hubgeometry package still scans the *whole* repo tree via `runtime.Caller`-derived repo root, but it is never invoked unless that package's own tests run. Batch 1's own verify includes that path, so it protects batch 1's own changes. Batch 2's verify (`go build ./... && go test ./internal/websterengine/...`) and the overview's plan-level verify (`go build ./... && go test ./internal/websterengine/... ./internal/planparser/...`) both omit it — so Card 3's own explicit "must NOT name a literal `_lyx`" requirement on the new `renderCardPointers` in `render.go` (exactly the risk this guard exists to catch) is never machine-checked by anything this plan actually runs after batch 1 completes.
**Fix:** Add `./internal/hubgeometry/...` to batch 2's `verify:` (and ideally the overview's top-level `verify:`, since it is the task's definitive completion gate) so the geometry-literal guard re-scans the repo after render.go's card-pointer rendering lands.
