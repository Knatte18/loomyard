## Fixed

- `20260808-170058-plan-review-r4.md` — "[BLOCKING] Card 18 prescribes a `Config.Dirs() == nil` assertion that cannot pass".
  Verified empirically by compiling and running `strings.Fields("")`: the result is **non-nil** with `len == 0`, because `strings.Fields` allocates via `make([]string, n)` even for `n == 0`.
  `Config.Dirs()` is `strings.Fields(c.Pathspec)` (`internal/fabricengine/config.go:27-29`), so a `== nil` assertion would have failed on every run regardless of anything this task changes.
  Card 18 now requires `len(cfg.Dirs()) == 0` (with `reflect.DeepEqual(cfg.Dirs(), []string{})` allowed as an alternative spelling) and explicitly forbids the `== nil` comparison, and its commit message was corrected off "nil Dirs()".
  The same wrong claim appeared in three further places and all were corrected: card 17's `strings.Fields("")` rationale, card 20's description of the production call site, and card 24's justification for passing `nil` to `IsReservedHubName`.
  Card 17's actual decision (the double-quoted empty string over a null scalar) is unaffected — that choice rests on `applyExistingOverrides` copying value, tag and style, not on the nil-vs-empty distinction.
  This error originated in `_mill/discussion.md`, which states "an empty value yields a nil slice cleanly"; the plan no longer repeats it.
- `20260808-170058-plan-review-r4.md` — "[NIT] Card 21's rationale for the retained `no_raddle_names` sub-test misdescribes `HostJunctions`".
  Verified: `HostJunctions`' doc comment (`internal/fabricengine/junction.go:50-55`) states it returns one record per name in `names`, in that slice's own order, and its body performs no `HubReservedNames`/`filterHubReserved` filtering.
  The sub-test therefore pins nothing about reservation enforcement; `TestFilterHubReserved` and `TestIsReservedHubName` own that property.
  Card 21 now forbids the inaccurate justification and supplies the accurate one — a scope guard that `HostJunctions` returns exactly the caller-supplied names and never augments them with a hub-structural entry of its own — so the reworded comment landing in the codebase is true.
