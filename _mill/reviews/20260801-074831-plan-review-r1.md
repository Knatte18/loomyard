## Findings

### [BLOCKING] fabriccli/fabric.go's per-worktree LoadConfig never migrated to repo-wide BoardDir
**Location:** Batch 3 (card 11) / Batch 4 (cards 14-18) / Batch 6, cross-cutting: `internal/fabriccli/fabric.go`
**Issue:** `runAdd`/`runList`/`runCheckout`/`runPairs`/`runReconcile`/`runPruneWithFlag`/`runCleanupWithFlags`/`runRemoveWithFlag` (fabric.go:280,317,378,411,443,472,501,531) all call `fabricengine.LoadConfig(cwd)`, which reads the PER-WORKTREE `<cwd>/_lyx/config/fabric.yaml` via `configengine.Load`. Card 11 stops `ReconcileAll` from ever materializing that per-worktree file (fabric becomes repo-wide, written only to `BoardDir` by clone/`ReconcileFabricAt`). No card updates these 8 call sites to load from `hubgeometry.BoardDir(l.Hub)` instead of `cwd`. After batches 3+4 land, every one of these 8 verbs — including `reconcile`, the exact remedy batch 6 retargets 8 "run lyx init" messages to — fails on any freshly-cloned or wired worktree with `configengine.Load`'s `"config file <cfgPath> not found; run \"lyx config reconcile\""` (which itself would not fix it, since `lyx config reconcile` also skips fabric per card 11). `internal/fabriccli/cli_test.go`'s `setupCLIRepo` manually writes a per-worktree `fabric.yaml` today, which will mask this regression in tests unless updated.
**Fix:** Add a card updating all 8 `fabricengine.LoadConfig(cwd)` sites in fabric.go to resolve `t.cfg` from `hubgeometry.BoardDir(l.Hub)` (after `l, err := hubgeometry.Resolve(cwd)`), and update `cli_test.go`'s fixtures accordingly.

### [BLOCKING] hostLayoutFor's Resolve(worktreeRoot) fallback breaks under the new cwd gate; card 2 vs card 4 self-contradict
**Location:** Batch 1, cards 2 and 4 (`internal/hubgeometry/hubgeometry.go`, `internal/fabricengine/hostlayout.go`)
**Issue:** `fabricengine.hostLayoutFor` (used by `Reconcile`/`Status`) falls back to `hubgeometry.Resolve(worktreeRoot)` — passing a worktree ROOT, not a real cwd — for any non-hub-sibling worktree. Under card 2's new at-or-below gate, for a subpath-anchored hub (anchor e.g. "backend"), `Resolve(worktreeRoot)` computes `rel = ".."` against `worktreeRoot/backend` and now hard-errors with `ErrCwdOutsideAnchor`, regressing a previously-working (if edge-case) recovery path into a per-pair resolve error. Card 4's own test requirement asks to assert this exact call "does NOT return ErrCwdOutsideAnchor" while simultaneously acknowledging "worktreeRoot is at-or-below only when it equals the anchor" — i.e. the card requires an assertion its own gate spec (card 2) contradicts.
**Fix:** Resolve the contradiction explicitly — either exempt `hostLayoutFor`'s worktree-root-as-cwd fallback from the gate, or rewrite card 4's assertion to match card 2's actual (error) behavior, and state which is correct in the batch scope.

### [BLOCKING] Card 12 offers a template-resolution option that risks a configsync↔fabricengine import cycle
**Location:** Batch 3, card 12 (`internal/configsync/configsync.go`)
**Issue:** Card 12 says resolve the fabric template "via `configreg.Template(\"fabric\")` (or `fabricengine.ConfigTemplate` if already imported)". `configsync` does not import `fabricengine` today, but batch 4 card 16 requires `fabricengine/clone.go` to call `configsync.ReconcileAll` — establishing `fabricengine -> configsync`. If batch 3's implementer picks the parenthetical `fabricengine.ConfigTemplate` alternative, `configsync` would import `fabricengine`, and batch 4 would then be unable to add `configsync` to `fabricengine` without a cycle. The card's own rationale ("reuse whatever ReconcileAll uses to avoid a new import cycle") argues against the very alternative it offers.
**Fix:** Remove the `fabricengine.ConfigTemplate` alternative from card 12's requirements; mandate `configreg.Template("fabric")` (already-imported, safe) only.

### [NIT] Clone anchor mismatch check cannot distinguish "unset --subpath" from "explicit root"
**Location:** Batch 4, cards 15 and 18 (`internal/fabricengine/clone.go`)
**Issue:** The adopt-path mismatch check treats `subpath == "" || subpath == "."` as "default/unset" and never errors in that case, silently adopting whatever anchor is recorded. Since the CLI flag's own default is `"."` (card 17), a user who explicitly re-clones with `--subpath .` expecting root cannot ever get the mismatch error against a repo actually anchored at a subpath — it silently adopts the subpath instead.
**Fix:** Document this as an accepted limitation in the batch scope, or give the CLI an unset sentinel distinct from `"."` if precise mismatch detection is wanted.
