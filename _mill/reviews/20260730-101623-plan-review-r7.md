## Findings

### [BLOCKING] settings.json permission set unverified against real precedent
**Location:** Batch 2, Card 11 (`settings.json`) / Card 8 (`run.sh`)
**Issue:** Card 11 pins exactly `Skill(prowler:*)` + `Bash(bash *)`, reasoning that `run.sh`'s child `go build` is "a grandchild of the permitted bash call, not a separately-gated Claude tool call." I read the actual reference plugin's live `settings.json` (`/home/knatte/Code/millhouse/wts/millhouse/plugins/weblens/settings.json`): it grants **three** entries — `Skill(weblens:*)`, `Bash(node *)`, `Bash(bash *)` — even though `run.sh` invokes `node` only via an internal `exec node "$SCRIPT_DIR/fetch.mjs"` inside the already-`Bash(bash *)`-permitted script (verified in `plugins/weblens/scripts/run.sh`), the exact same relationship prowler's `go build` has to its own wrapper. This is real, in-context, Read-able evidence that directly contradicts the plan's stated permission-model claim.
**Fix:** Either add an explicit `Bash(go *)` (and/or `Bash(<bin-path> *)` for the final `exec "$BIN"`) entry mirroring weblens' `Bash(node *)`, or add a card/discussion note showing this was deliberately checked against the weblens precedent and found unnecessary — do not ship the two-entry set on the untested assumption that subprocess spawns need no separate grant.

## Verdict

REQUEST_CHANGES
Settings.json's permission set contradicts weblens' own verified precedent for gating a wrapper's spawned child process.
