### [BLOCKING:design] "All four take loose scalars" is false for two of them
**Section:** `### stencilstore-ownership` → Decisions (line 237).
**Issue:** The document says of the four treadle read sites: *"All four take loose scalars rather than a struct, so a new field alone reaches none of them: the directory arrives as a new field **and** as a parameter threaded through those four functions from their callers in `run.go`."* The source refutes it. `judgeInputs` is a struct (`internal/treadleengine/judge.go:34-35`), and `runCircling` (`judge.go:50`) and `runMilestone` (`judge.go:64`) both take `in judgeInputs`. Their callers build it as a composite literal at `internal/treadleengine/run.go:322` and `run.go:357`, so one new `judgeInputs` field reaches both. Only `runTriage` (`judge.go:140`) and `runTargeting` (`internal/treadleengine/targeting.go:24`) take loose scalars. The premise is wrong, and it over-prescribes the mechanism a plan writer will implement.
**Fix:** Replace that sentence with: *"Two of the four — `runCircling` (`judge.go:50`) and `runMilestone` (`judge.go:64`) — take a single `judgeInputs` struct (`judge.go:35`), built as a literal by their callers at `run.go:322` and `run.go:357`, so one new `judgeInputs` field reaches both. The other two — `runTriage` (`judge.go:140`) and `runTargeting` (`targeting.go:24`) — take loose scalars and need one new parameter each. The directory therefore arrives as a caller-supplied field on the engine, plus one new `judgeInputs` field and two new function parameters, every one of them set from `run.go`."* Knock-on edits forced by the same change: (a) the `treadleengine` row of the per-engine table (line 230) reads *"threaded from `run.go` into the four template-reading functions named below"* — append *"— through `judgeInputs` for the two judge calls and a new parameter for triage and targeting"*; (b) line 235's enumeration is correct and needs no change; (c) Q&A line 613's answer (*"As a new caller-supplied field … passed in by the round runner"*) stays true and needs no change. Options for how the two judge calls receive it: a `judgeInputs` field, or a fifth loose parameter. Recommend the `judgeInputs` field — it is the existing bundling idiom for exactly these two callers, it touches two call sites instead of four, and it keeps the Treadle Runner-Seam Invariant's actual rule ("treadle is *told* its geometry", CONSTRAINTS.md) visibly satisfied because the value is set in a caller-owned literal.

### [BLOCKING:design] Pre-run seeding's mutation record has no stated disposition
**Section:** `## Constraints` → Mutation Record Invariant bullet (lines 498-500), and `### seeding-trigger`.
**Issue:** The seeding verb is specified as a mutating fabric verb carrying a `*Mutations` record, and the document says *"`lyx stencil sync`'s envelope therefore carries the fixed `mutations` array and `partial` bool like every other mutating verb outcome"* — but `sync` is the rare trigger. The normal trigger is `cmd/lyx`'s root pre-run, which fires under **every** command (`lyx board add`, `lyx webster run`, …). Nothing states what happens to the record there. A run of `lyx board list` that writes 15 files and creates a board commit would either report nothing, or widen `board`'s envelope key set — and `### drift-notification-channel` explicitly rejects widening the key set for every command. A plan writer must invent the answer.
**Fix:** Add a sentence to the Mutation Record Invariant bullet, after *"…per that invariant's pre-flight carve-out."*: *"Outside `lyx stencil sync` the verb runs from the root pre-run, which emits no verb-outcome envelope; the record is therefore not surfaced in the triggering command's envelope — a pre-run seed is logged via `logger.Warn`/`logger.Info` and left out of the key set, since CONSTRAINTS.md scopes the fixed `mutations`/`partial` keys to a verb outcome and `drift-notification-channel` already rejects widening every command's key set."* Options: (a) drop the record outside `stencil sync`, logging it; (b) add `mutations`/`partial` to every command's envelope; (c) make the pre-run seed emit its own standalone envelope line. Recommend (a): CONSTRAINTS.md's Mutation Record Invariant binds the key set only "for every envelope emitted from a **verb outcome**", and (b) contradicts this document's own line 330 rejection of a new envelope field. Knock-on edits: `### seeding-trigger`'s sentence *"The composition root hands that list to the `board.lock`-taking `fabricengine` commit verb."* gains *"…and logs, rather than envelopes, the record that verb returns"*; and `## Testing`'s **Mutation record** paragraph (line 579) gains *"and assert a non-`stencil` command's envelope key set is unchanged by a run that seeded."*
