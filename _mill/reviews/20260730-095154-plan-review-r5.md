## Findings

### [BLOCKING] run.sh's build-lock never releases on the real (non-BUILD_ONLY) run path
**Location:** Batch 2, Card 8 (`run.sh`)
**Issue:** `run_or_exit`'s non-`PROWLER_BUILD_ONLY` branch is `exec "$BIN" "$@"`. `exec` replaces the shell's process image without going through bash's normal exit sequence, so a `trap ... EXIT` set earlier in the same script never fires — the card's own claim ("call run_or_exit (the trap releases the lock on exit)") is false for this branch. After any real first build, `.build.lock` is left on disk forever; the next time a fresh build is genuinely needed (bin/ removed) `mkdir "$LOCK"` fails immediately and every waiter stalls for the full ~300s staleness window before reclaiming, even with zero live builders.
**Fix:** In `run_or_exit`'s exec branch, explicitly release the lock (check token ownership, `rm -rf "$LOCK"`) immediately before `exec`, rather than relying on the EXIT trap; add a selftest.sh assertion that invokes `run.sh` without `PROWLER_BUILD_ONLY` (e.g. with no URL args, so the child just prints Usage and exits 1) and checks the lock dir is gone afterward — the current harness only ever sets `PROWLER_BUILD_ONLY=1`, so it never exercises the `exec` branch and would pass despite this bug.

### [BLOCKING] chromedp fallback has no render/network-idle wait before capturing HTML
**Location:** Batch 1, Card 7 (`browser.go` / `fetchWithBrowser`)
**Issue:** The card specifies `chromedp.Run` a bare `Navigate(url)` then immediately `chromedp.OuterHTML("html", &html, ...)`. `chromedp.Navigate` blocks only until the page's `load` event fires, not until JS-driven/async content has rendered. Weblens' reference behavior (`_mill/discussion.md`'s Technical context) explicitly used Puppeteer's `networkidle0` before extraction — precisely because the browser fallback's whole purpose is JS-rendered content that isn't present at `load` time. No wait/idle/selector step is specified anywhere in Card 7, so the ported fallback can systematically capture pre-render HTML for exactly the case it exists to handle.
**Fix:** Add an explicit post-navigate wait to Card 7's requirements — e.g. `chromedp.Sleep(~1-2s)` or polling network-idle via the CDP `Network` domain — before `OuterHTML`, and note it as a deliberate parity substitute for Puppeteer's `networkidle0` (chromedp has no built-in equivalent action).

### [NIT] Lock timeout silently diverges from discussion.md's ~120s to the plan's ~300s
**Location:** Batch 2, Card 8 and Card 9; vs. `_mill/discussion.md`'s build-on-first-run decision
**Issue:** discussion.md (the stated authoritative spec) fixes the acquire/staleness timeout at "~120 s" in two places; Card 8/Card 9 both use "~300s" (with inline rationale about Windows AV-scan overhead) but this change is not recorded as a Shared Decision override, unlike the flat-vs-versioned layout change which got its own explicit `### Decision:` in the overview.
**Fix:** Add a one-line Shared Decision (or batch-local decision) documenting the 120s→300s change and its rationale, matching the treatment given to the layout override.
