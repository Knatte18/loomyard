## Findings

### [NIT:design] Card 9's new launcher-filename test may not exercise the real write path
**Location:** batch 2 (launchers) / card 9 **Issue:** The new scenario must prove "the written run launcher's filename is still `run`+ext" while staying Tier 1 (no `hubforge.NewHub`), but every existing test that calls the actual `writeLaunchers` (the only place that constructs the real `runPath`) is `//go:build integration`-tagged (`launchers_containment_integration_test.go`, `add_rollback_adopt_test.go`, `livestate_*_test.go`); nothing in the package currently exercises `writeLaunchers` untagged. Following "same shape as the file's existing cases" (pure `launcherScript`/`launcherExt` calls) risks a tautological check that never touches `launchers.go`'s own `filepath.Join(launcherDir, "run"+ext)`, so it would not actually catch a future rename to `start<ext>`. **Fix:** Card 9 should spell out the mechanism (e.g. hand-build a `*lyxcwd.Location` over `t.TempDir()` and call `writeLaunchers` directly, pre-seeding the menu-launcher path so `PrimeName` is never reached) rather than leaving it to be discovered at implementation time.

### [NIT:consistency] Batch 4's dependency rationale argues for the opposite order
**Location:** `_mill/plan/04-skill-rename.md` (batch 4) depends-on batch 3 **Issue:** The batch says it depends on batch 3 "because `internal/shedadapters/bouncer_seed_test.go` already names `ly-drive` in a comment by then, and the skill should exist under that name before anything else in the tree refers to it" — but the stated DAG has go-comment-sweep (batch 3, which writes that comment) land *before* skill-rename (batch 4, which creates the `ly-drive` path), so for the span between batches 3 and 4 the tree contains a comment naming a skill path that does not yet exist, the reverse of the principle cited. No functional or test impact (it's a Go comment), but the rationale contradicts the order it's attached to. **Fix:** Either swap the dependency direction (skill-rename before comment-sweep) or replace the rationale with one that actually supports comment-sweep-first (e.g. "the whole task lands as one unit; ordering here only needs to avoid a mid-task PR review reading a stale name").
