## Findings

### [NIT] Card 47's weft-path guidance offers two options, one of them wrong
**Location:** batch 8 / card 47 **Issue:** the card tells the implementer to resolve the weft worktree path either via "`HostJunctions(l, slug, names)`'s first record's Target parent" or "more robustly, `WeftWorktreePath(l, slug)`" — but `filepath.Dir(junctions[0].Target)` only equals `WeftWorktreePath(l, slug)` when `AnchorRel == "."`; in a subpath-anchored repo it resolves to `WeftWorktreePath(l, slug)/<AnchorRel>`, a subdirectory, not the worktree root. Presenting the incorrect option first (even if functionally harmless here, since `git rev-parse --git-path` walks up to find the enclosing repo regardless of starting subdirectory) risks an implementer picking the fragile phrasing over the correct one. **Fix:** state only `WeftWorktreePath(l, slug)` as the resolution, dropping the "first record's Target parent" alternative.
